# pool 두 개 사이 실제 이동과 극단 부하 (2026-11-05)

[cap sweep 8절](../cap-sweep-20261104/README.md#8-실측-16코어-pool-하나-2026-11-05)은 16코어 pool 하나에서 "옮기면 얼마나 되찾나"를 계산만 했다. 이 문서는 bud05 NUMA 0을 15코어 pool 두 개로 나눠 노드 두 개로 보고, sandbox를 실제로 옮긴다.

## 0. 결론

1. **배치 때는 burst를 알 수 없어서 한 노드만 넘치는 때가 생긴다.** 넓게 쓰는 sandbox의 40%는 수명의 4분의 1이 지난 뒤에야 처음 넓게 쓴다(4절). container 수로 고르는 배치에서 기다린 시간 중 한 pool만 꽉 찼을 때 생긴 몫은 사용률 41~83%에서 49~71%다. GRPO group 하나가 한 노드에 몰리면 85%다.
2. **slowdown은 사용률에 비선형이다.** CPU 가중 slowdown은 사용률 41%, 65%, 83%, 95%에서 1.35, 1.84, 2.52, 4.26이다. 한 노드에 몰린 group은 노드 평균 사용률이 38%여도 tool 시간이 2.87배다.
3. **바쁜 목적지로 옮겨도 되찾는다.**
   - 섞인 부하(사용률 41~83%)에서 60 ms 이동은 공유 pool 대비 대기 차이의 61~96%를 되찾는다. 5초 이동은 10~14%다. 경합 episode가 몇 초짜리라서 반응 속도가 중요하다.
   - 한 노드에 몰린 group은 group 완료 시간이 1.39배에서 1.22배로 준다. 미리 나눈 배치나 공유 pool과 같다. 이 지속형 과부하에서는 5초 이동도 같은 결과를 낸다.
4. **이득에는 한계가 있다.**
   - 명령 시간 개선은 대기 감소보다 작다. K=120에서 대기는 19% 줄지만 CPU 가중 slowdown은 6%만 준다(같은 조건 2회 차이 수준). clock 저하와 짧은 명령의 지연은 같은 socket 안에서 옮겨서는 줄지 않는다.
   - 사용률 95%에서는 단순한 이동 규칙이 거의 듣지 않는다. 공유 pool은 그때도 대기를 38% 줄인다.
   - rollout 수준에서는 LLM 대기에 묻힌다. K=120 rollout p99는 1.58에서 1.50이 된다(2회 평균).
   - 같은 trace 사본이 함께 시작하면(묶인 순서) 노드 전체가 넘쳐서, 공유 pool도 tool 시간을 줄이지 못했다.
5. **motivation으로 보면** hand-off가 맞는 자리는 사용률 60~85%의 섞인 부하에서 생기는 몇 초짜리 국소 경합이다. 반응이 5초에서 60 ms로 빨라지면 되찾는 몫이 10~14%에서 61~96%로 바뀐다. 수십 초 이어지는 몰린 group은 migration으로도 된다. 단 이 비교는 migration 비용을 뺀 낙관적인 값이다(7절).

## 1. 방법

| 항목 | 설정 |
|---|---|
| 노드 | CPU 2-16, 17-31을 각각 pool 하나로 본다. controller는 CPU 0-1(극단 실험은 sibling 64-65 포함). SMT sibling 66-95는 비워 둔다. governor `performance`, turbo 켜짐 |
| 이상적 상한 | 두 pool을 합친 30코어 pool 하나(shared). 경합을 노드 경계 없이 나누는 경우다 |
| trace | cap sweep 8절과 같은 48개(넓은 24, 좁은 24). 기록된 LLM 간격을 넣는다(`--schedule gaps`) |
| 배치 | 새 sandbox는 지금 container 수가 적은 pool에 들어간다(`experiment.py --pools`). 배치 때는 어떤 sandbox가 언제 넓게 쓸지 모른다 |
| 이동 | `real_cap.Mover`. 20 ms마다 container별 CPU 사용량과 PSI cpu some을 읽는다. pool이 꽉 차고(크기 − 0.5코어 이상 사용) container가 평균 반 개 이상 기다리면 경합이다. 경합이 d초 이어지면, 최근 0.5초 동안 가장 많이 기다린 container의 cgroup `cpuset.cpus`를 다른 pool로 바꾼다. 다음 이동에는 다시 d초가 필요하다. 옮긴 container는 5초 동안(`-hold30` 조건은 30초) 다시 옮기지 않는다 |
| 이동 비용 | cpuset 쓰기는 약 5 ms다(p50). 메모리는 그대로 node 0에 있고 CPU만 바뀐다. hand-off의 이상적인 경우다. d = 0.06초는 감지 50 ms + hand-off 10 ms, d = 5초는 pre-copy migration 수준이다 |
| 목적지 규칙 | free: 경합이 아니고 빈 코어가 4개 이상인 pool. gain(극단 실험): 그 container가 받을 코어가 지금보다 1.5배 이상이고 1코어 이상 많은 pool. 목적지가 바빠도 된다. 받을 코어는 container마다 같은 몫(cgroup `cpu.weight`가 같다)이라 보고 water-filling으로 계산한다 |
| 비교 | 명령마다 cap sweep 8절의 cap 없음 K=4 시간(사용률 약 5%)과 비교한다. 지표 정의는 cap sweep 8절과 같다 |

## 2. 시작 순서: 묶인 순서와 섞은 순서

처음 두 pool 실행은 `experiment.py`가 대기열을 기록된 첫 명령 시각으로 정렬한 상태에서 돌렸다. 48개 trace를 8번씩 넣은 384개에서 같은 trace 사본 8개가 연달아 시작했다. replay라 사본은 같은 명령을 같은 시각에 실행한다. 같은 task의 rollout 8개가 함께 시작하는 GRPO group의 상한이다(실제 rollout은 LLM 출력이 달라 곧 어긋난다). harness를 고친 뒤 무작위로 섞은 순서로 다시 돌렸다.

K=60(코어당 2개), 사용률 약 40%, 조건마다 1회.

| 조건 | 묶인 순서: tool 시간 | 묶인 순서: 초당 대기 | 섞은 순서: tool 시간 | 섞은 순서: 초당 대기 |
|---|---|---|---|---|
| static | 1.50 | 1.72 | 1.225 | 0.552 |
| 5초 이동 | 1.38 | 1.26 | 1.202 | 0.523 |
| 1초 이동 | 1.57* | 1.42 | 1.186 | 0.479 |
| 60 ms 이동 | 1.52 | 1.62 | 1.185 | 0.377 |
| 30코어 공유 | 1.53 | 1.40 | 1.191 | 0.345 |

초당 대기는 모든 container의 PSI cpu some 합(초/초)이다. \*묶인 순서의 1초 이동은 harness 오류(생성 중인 container의 빈 cpuset)로 sandbox 102개를 잃어 명령 수가 다른 조건의 70%다.

- **묶인 순서에서는 공유 pool도 tool 시간을 줄이지 못한다(1.53 대 1.50).** 두 pool이 함께 꽉 찬 시간이 6.6%로, 독립이라면 기대할 1.1%의 6배다. 같은 trace 사본 8개가 함께 빌드하면 노드 전체가 넘쳐서 옮길 곳이 없다. 5초 이동만 1.38로 나았다. 1회라 잡음과 구별하기 어렵지만, 긴 과부하에서 느린 이동이 나은 tsunami 결과(5.1절)와 같은 방향이다.
- **섞은 순서에서는 두 pool이 함께 꽉 차는 일이 드물다(0.7%).** 기다린 시간의 71%가 한 pool만 꽉 찬 시간에 생겼고, 그때 다른 pool에는 빈 코어가 중앙값 11개 있었다.

## 3. 섞은 순서: 반응 시간별 회수

이동 규칙은 free(빈 코어 4개 이상인 pool로만)다.

| 조건 | 사용률 | tool 시간 | 넓은 / 좁은 | CPU 가중 | 무거운 명령 p50 / p90 | 초당 대기 | pool당 경합 시간 | 이동 (분당) |
|---|---|---|---|---|---|---|---|---|
| static | 40.8% | 1.225 | 1.29 / 1.13 | 1.35 | 1.20 / 1.79 | 0.552 | 6.3% | 0 |
| 5초 이동 | 40.8% | 1.202 | 1.25 / 1.13 | 1.30 | 1.19 / 1.75 | 0.523 | 6.1% | 19 (0.9) |
| 1초 이동 | 41.8% | 1.186 | 1.23 / 1.12 | 1.28 | 1.18 / 1.63 | 0.479 | 5.9% | 109 (5.4) |
| 60 ms 이동 | 40.0% | 1.185 | 1.24 / 1.10 | 1.27 | 1.18 / 1.53 | 0.377 | 4.7% | 267 (13.0) |
| 30코어 공유 | 43.4% | 1.191 | 1.22 / 1.15 | 1.25 | 1.18 / 1.62 | 0.345 | 4.4% | – |

static과 공유 pool 사이의 대기 차이(0.207) 중 되찾은 몫은 5초 이동 14%, 1초 35%, 60 ms 85%다.

1. **빨리 옮길수록 많이 되찾는다.** 60 ms 이동은 공유 pool에 가깝고, 무거운 명령 p90은 공유 pool보다 낮다(1.53 대 1.62). 5초 이동은 static과 거의 같다. 섞은 순서에서는 경합 episode가 짧아서(cap sweep 8.6절, 손실 가중 p50 5.6초) 5초 뒤에는 이미 끝난 경우가 많다.
2. **옮긴 것은 거의 넓은 sandbox다(93~100%).** 목적지가 2초 안에 꽉 차는 경우가 61~79%지만, 대기 합은 줄었다. 좁은 sandbox는 경합 때 다 합쳐 1코어쯤만 쓰므로 옮길 이유가 없다.
3. **공유 pool의 tool 시간은 이상적 상한보다 나쁘게 나온다.** sandbox가 `nproc` 30을 보고 worker를 더 띄워 넓은 sandbox의 CPU 시간이 18% 늘었다(15코어 pool은 8~10%). 더 많은 코어가 바빠져 clock도 3.70에서 3.55 GHz로 떨어졌다. 그래서 tool 시간은 60 ms 이동(1.185)과 공유 pool(1.191)이 같다.
4. **사용률 40%에서는 절대 이득이 작다.** tool 시간이 1.225에서 1.185로 3% 준다. 남은 slowdown(좁은 sandbox 1.10~1.15)은 대부분 clock이다. 기준 K=4는 4.02 GHz, K=60은 3.42~3.70 GHz다.

## 4. 배치 때 burst를 알 수 없다

10-14 Docker profile(264개 trace, 100 ms 평균)에서 sandbox가 처음 8코어 이상을 쓰는 시점을 봤다(`cap_sweep.py bursts`). 시각은 LLM 대기를 포함한 sandbox 수명 기준이다. 아래 비율은 burst가 있는 150개 기준이다.

| 항목 | 값 |
|---|---|
| 8코어 이상 burst가 있는 trace | 150개 / 264개(57%) |
| 첫 burst 시각 p10 / p50 / p90 | 14 / 50 / 142초. 수명의 5% / 21% / 73% |
| 수명의 25%, 50%가 지난 뒤 첫 burst | 40%, 17% |
| 첫 60초 안에 burst | 59% |
| 따로 떨어진 burst 수(5초 넘게 떨어짐) p50 / p90 | 4 / 8 |

배치는 생성 시점에 한 번 정해진다. 넓게 쓰는 sandbox의 40%는 수명의 4분의 1이 지난 뒤에야 처음 넓게 쓰고, 한 sandbox가 따로 떨어진 burst를 4번쯤 낸다. 생성 시점의 부하나 image만으로는 언제 어느 노드가 넘칠지 정할 수 없다. 섞은 순서 static에서 한 pool만 꽉 찬 시간에 다른 pool이 11코어를 비워 둔 것(2절)이 그 결과다.

## 5. 극단 부하 (`extreme.py`)

같은 두 pool에서 부하를 키우고, 한 pool에 burst를 몰아넣었다. controller는 CPU 0-1과 sibling 64-65를 쓴다(극단 부하에서는 harness 인스턴스가 여러 개라서). 이동 규칙은 gain(바빠도 더 많이 받을 pool로)을 기본으로 했다. 조건마다 1회, K=120 static과 gain은 2회 돌렸다.

| 실험 | 구성 |
|---|---|
| tsunami | 배경 K=40(섞은 320개, 사용률 약 38%)에 wave 4개를 60, 420, 780, 1140초에 넣는다. wave 하나는 넓은 trace 하나(hugo, fmt, preact, caddy)의 사본 8개를 함께 시작한 것이다. GRPO group 하나가 한 노드에 몰린 경우다. local은 8개를 모두 pool 2-16에, spread는 container 수가 적은 pool에 나눠(배치 때 미리 안다면), shared는 30코어 pool 하나에 넣는다 |
| 부하 sweep | K=90, 120, 150. 섞은 5K개를 같은 순서로 넣는다. 사용률 65%, 83%, 95%다. K=60은 3절의 섞은 순서 결과다 |
| wave 지표 | group 완료 시간 = 사본 8개 중 마지막 끝 − 처음 시작, 같은 trace를 K=4에서 혼자 돌린 시간으로 나눈다. 동기 RL에서 group 하나의 step 시간이다 |
| 되찾은 대기 몫 | (static 대기 − 조건 대기) ÷ (static 대기 − 30코어 공유 pool 대기). 대기는 모든 container의 PSI cpu some 합(초/초)이다 |

### 5.1 tsunami: 한 노드에 몰린 GRPO group

|---|---|---|---|---|---|---|---|

\*spread의 caddy wave에서 사본 하나가 명령 하나(보통 8초)에 308초 멈췄다. 그동안 CPU를 34초만 썼으니 경합이 아니라 replay 정지다. 이 wave를 빼고 hugo, fmt, preact 세 wave만 쓴 값이다. 넣으면 group 완료 시간 평균 1.57, 최악 2.57이다.

1. **한 노드에 몰리면 그 group만 크게 느려진다.** wave 사본의 tool 시간은 2.87배다. 배경 sandbox는 1.26배로 덜 다친다. 기다린 시간의 85%가 한 pool만 꽉 찬 시간에 생겼다. 다른 pool은 그동안 비어 있었다.
2. **옮기면 미리 나눈 배치나 공유 pool만큼 회복한다.** 60 ms gain은 group 완료 시간을 1.39에서 1.22로, 최악 group을 1.53에서 1.28로 줄인다. 배경은 손해가 없다. 배치 때 burst를 몰라도, 넘친 뒤에 옮기면 미리 안 것과 같다.
3. **이런 지속형 과부하에서는 5초 이동도 충분하다.** 사본 8개가 같은 빌드를 수십 초 동안 함께 돌린다. 5초 늦어도 대부분 시간이 남아 있다. 5초 gain은 25번만 옮겼고 그중 76%가 wave 사본이었다. 옮긴 container는 CPU를 중앙값 3.0배 더 받았다.
4. **60 ms gain은 같은 container를 여러 번 옮겼다.** 186번 중 40개 container가 두 번 넘게 옮겨졌고(최대 8번), wave 사본이 원래 pool로 31번 돌아왔다. 0.5초 평균 사용량으로 목적지를 고르고, 옮긴 container를 5초만 묶어 두기 때문이다. 이동 4번 중 1번은 CPU를 오히려 덜 받았다(p25 0.85배). 30초 묶어 두면 대기가 1.04에서 0.87로, 최악 group이 1.28에서 1.23으로 준다. 이동 수는 179번으로 비슷하다. 다른 container가 대신 옮겨진다.

K=120의 되찾은 몫은 static 2회 평균(5.45)을 기준으로 했다. K=60은 3절의 섞은 순서 결과(free 규칙, `contention.json`, 384개)라서 다른 행과 trace 수와 controller가 조금 다르다.

1. **slowdown은 사용률에 비선형이다.** static의 CPU 가중 slowdown은 사용률 41%, 65%, 83%, 95%에서 1.35, 1.84, 2.52, 4.26이다. 무거운 명령 p99는 95%에서 13.9배다. 늘어난 몫(0.35 → 0.84 → 1.52 → 3.26)이 1/(1 − 사용률)처럼 커진다.
2. **사용률 65~83%에서는 60 ms 이동이 공유 pool에 가깝다.** 되찾은 대기 몫은 K=90 gain 96%, K=120 gain 61%(30초 묶음 78%), free 86%다. 5초 이동은 K=120에서 10%, K=60에서 14%만 되찾는다. 이 부하에서는 경합 episode가 몇 초짜리라 5초 뒤에는 이미 지나가 있다.
3. **명령 시간 개선은 대기 감소보다 작고 확실하지 않다.** K=120에서 gain은 대기를 19% 줄였고, 두 번 모두 재현됐다. 하지만 CPU 가중 slowdown은 2회 평균 2.54에서 2.40으로 6%만 준다. 이 차이는 같은 조건 2회 사이 차이(2~7%)와 비슷하다. 사용률이 높으면 clock이 3.3 GHz로 떨어지고(기준 4.02), 짧은 명령도 1.6배 느려진다(명령별 비율 중앙값). 이 몫은 같은 socket 안에서 옮겨서는 줄지 않는다.
4. **사용률 95%에서는 이 이동 규칙이 거의 듣지 않는다.** 두 pool이 함께 꽉 찬 시간이 50%다. gain은 대기를 2%만 줄이고(되찾은 몫 4%) 명령 시간은 그대로다. 30코어 공유 pool은 같은 부하에서도 대기를 38% 줄인다(CPU 가중 3.96). 두 pool 모두 꽉 차 있어도 기다리는 container 수가 한쪽에 더 많은 때가 있고, 공유하면 그 차이가 바로 고르게 나뉜다. gain 규칙은 받을 코어가 1.5배 넘게 느는 목적지가 있어야 옮기는데, 양쪽이 다 꽉 차면 그런 목적지가 드물다. 그래서 분당 12번만 옮겼고, 이 차이를 따라가지 못했다. 묶인 순서의 K=60(2절)에서는 공유 pool도 tool 시간을 줄이지 못했다.
5. **rollout 수준에서는 LLM 대기에 묻힌다.** K=120에서 rollout p99는 static 1.54~1.62, gain 1.46~1.54다. tsunami의 group 완료 시간은 1.39에서 1.22로 줄어 차이가 더 크다. 동기 RL에서 넘친 노드에 있던 group의 step 시간이다.

## 6. 처음 가설과 비교

| 가설 | 결과 |
|---|---|
| 하드웨어가 감당할 수 없는 burst가 오면 slowdown이 비선형으로 커진다 | 맞다. 5.2절 1. tsunami에서도 노드 평균 사용률은 38%인데 몰린 group의 tool 시간은 2.87배다 |
| 조금 바쁜 노드라도 옮기면 낫다 | 한쪽만 넘칠 때는 맞다. gain 이동의 목적지는 80~97%가 2초 안에 꽉 찼다. 그래도 옮긴 container는 CPU를 중앙값 1.3~1.5배 더 받았고, 전체 대기는 19~39% 줄었다. 단 이동 4번 중 1번은 CPU를 덜 받았다(p25 0.67~0.85배). 양쪽이 다 넘치는 95%에서는 이 규칙이 거의 듣지 않는다. 다만 공유 pool은 그때도 대기를 38% 줄이므로 나눌 여지는 남아 있다 |
| 배치 때 sandbox의 사용량을 알 수 없어서, 한 노드만 넘치고 다른 노드는 남는 때가 생긴다 | 맞다. 4절. container 수로 고르는 배치에서 기다린 시간 중 한 pool만 꽉 찼을 때의 몫은 tsunami 85%, K=60 71%, K=90 52%, K=120 49~50%, K=150 36%다 |
| 그래서 빠른 hand-off가 필요하다 | 경합 episode가 짧을 때만 맞다. 사용률 40~83%의 섞인 부하에서는 60 ms가 5초보다 훨씬 많이 되찾는다(85% 대 14%, 61~86% 대 10%). 한 group이 수십 초 동안 함께 빌드하는 tsunami에서는 5초 이동도 똑같이 회복한다 |

## 7. 한계

- **노드 두 개, 같은 socket이다.** 두 pool은 L3와 turbo 예산을 함께 쓴다. 그래서 옮긴 뒤 cache를 다시 채우는 비용이 거의 없고, 한가한 노드로 옮겨도 clock은 오르지 않는다. 앞의 것은 결과를 낙관적으로, 뒤의 것은 비관적으로 만든다. 노드가 많으면 목적지 선택지가 늘지만, 이 실험은 그것을 재지 않는다.
- **이동은 cpuset만 바꾼다.** 메모리는 node 0 DRAM에 그대로 있다. CXL tax와 hand-off의 실제 정지 시간이 없다. 5초 이동은 비용 없는 이동을 5초 늦춘 것이다. 실제 pre-copy migration은 출발 노드 CPU를 쓰고, burst 중인 VM의 dirty page 때문에 더 오래 걸린다. 그래서 5초 행은 migration에 낙관적이다.
- **이동 정책은 단순하다.** 0.5초 평균 사용량으로 목적지를 고르고, 옮긴 container를 5초만 묶어 둔다. 60 ms gain은 같은 container를 여러 번 옮겼다(5.1절 4).
- **30코어 공유 pool은 깨끗한 상한이 아니다.** sandbox가 `nproc` 30을 보고 worker를 더 띄워 CPU 시간이 15코어 pool보다 4~10% 더 늘었다. 그래서 상한 비교는 대기로 했다.
- **Docker replay다.** 명령마다 `docker exec`라서 고부하에서는 제어 경로도 느려진다. 다른 node에 몇 KB가 잡히면 harness가 sandbox를 끊는다(조건마다 1~44개, K=120에서 약 7%). 대기열은 조건마다 같지만, 끊긴 sandbox는 조건마다 다르다.
- **대부분 조건은 1회다.** K=120 static과 gain만 2회 돌렸다. 2회 사이 차이는 CPU 가중 2~7%, 대기 1~5%, 무거운 명령 p99 21~26%다.

## 8. 파일과 재현

| 파일 | 내용 |
|---|---|
| `pools-shuffled-analysis.json` | 2~3절 섞은 순서 K=60 5개 조건(`real_cap.py pools-analyze --runs runs-pools`) |

원시 결과(명령별 events, container별 cgroup 시계열, 이동 기록, host perf)는 bud05 `experiments/contention/.local/real/`의 `runs-pools/`, `runs-pools-grouped/`, `runs-extreme/`에 있다(Git 제외).

```bash
PY=/Serverless/agent-sandbox-cxl/venv/bin/python   # numba
C=experiments/contention
$PY $C/real_cap.py pools-run --runs runs-pools      # 2~3절, 5개 조건 약 2.5시간
$PY $C/real_cap.py pools-analyze --runs runs-pools
$PY $C/cap_sweep.py bursts                           # 4절
$PY $C/extreme.py run                                 # 5절, 22개 조건 약 11시간
$PY $C/extreme.py analyze
```

`run`은 workload CPU와 sibling의 governor가 performance가 아니면 실행을 거부하고, host 1분 load가 4 밑으로 내려갈 때까지 기다린다. bud05의 docker daemon은 SMT를 켜기 전에 떴다. 그래서 sibling CPU(64-65)를 `--cpuset-cpus`에 넣으면 거부된다. `contention-dense.json`의 `budget_cpus`가 budget container를 0-1에 둔다.
