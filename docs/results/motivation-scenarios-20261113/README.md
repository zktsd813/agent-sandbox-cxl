# hand-off와 vCPU 이동의 motivation 시나리오 (2026-11-13)

질문: 실행 중인 sandbox를 다른 노드로 ms 안에 넘기는 방식(hand-off)이나 vCPU만 옮기고 장치는 원래 host에 두는 방식(FragVisor형)은 어떤 상황에서 필요한가?

방법은 네 가지다.
- 외부 자료 조사: sandbox 플랫폼, agent RL infra, 노드 사이 분산 연구(6장).
- 기존 측정 자료 재분석: 명령 길이, LLM 대기, 명령 경계의 상태 크기(3.1, 3.5, 3.6).
- simulator: 명령 시작 때 옮기기, 실행 중 hand-off, 대기 중 미리 옮기기, network 복사, CXL tax를 같은 틀에서 비교했다. Codex가 구현하고 돌렸다([boundary-vs-handoff-20261113](../boundary-vs-handoff-20261113/README.md)).
- 실측 하나: 이전 상태는 CXL, 무거운 명령만 DRAM일 때의 tax(3.12, bud05).

여기서 "11-12 파일럿"은 agent workload 측정 파일럿이다. 결과는 bud05 `~/agent-sandbox-cxl/docs/results/agent-workload-20261112/`에, 명령 분류 `cmdkind.py`는 `~/agent-sandbox-cxl/experiments/workload-char/`에 있다(둘 다 git 밖). 이 디렉터리의 스크립트는 bud05의 두 checkout(`~/agent-sandbox-cxl`, `~/agent-sandbox-cxl-latest`)과 그 안의 git 밖 원자료를 읽는다.

## 0. 결론

1. **가장 강한 시나리오는 무거운 명령이 시작할 때 코어가 남는 노드에서 돌리는 것이다(S1).** 업계는 이미 노드 안에서 명령마다 코어를 붙인다(ARL-Tangram). 이것을 노드 밖으로 넓힌다.
   - 다언어 build·test 작업에서 이상적 공유(pool) 이득의 70~78%를 되찾는다(simulator).
   - 같은 CPU 가중 SLO(≤ 1.10)에서 노드가 48코어면 26%, 96코어면 16%, 192코어면 7% 이상 덜 든다. 256코어에서는 어떤 정책도 9.5%를 넘을 수 없다. 노드가 클수록 이득이 준다.
   - 이동 시간은 명령 시간에 더해진다. CPU 가중으로는 100 ms까지 괜찮고, 무거운 명령의 tail까지 지키려면 10 ms 안이어야 한다. 1초면 tail이 아무것도 안 할 때보다 나빠진다.
2. **LLM 대기 중에 미리 옮기기(리뷰어 Q3)는 이것을 대신하지 못한다.**
   - 다음 명령을 아는 oracle도 52~56%다. 대기 시작 때 본 부하가 명령 시작 때는 낡아 있다.
   - 이력으로 예측하면 39~45%이고 이동의 74%가 헛이동이다(3.5, 3.11).
3. **실행 중 이동은 설 자리가 거의 없다.**
   - 명령 시작 때 옮기기에 더하는 몫이 6~14%p이고, 노드 수 차이는 48코어에서만 보인다(3.2, 3.3).
   - 실행 중에 옮기려면 sandbox가 CXL에서 돌아야 한다. 그러면 무거운 명령이 tax를 낸다. 무거운 명령 tax가 1~2%만 넘어도 DRAM에서 시작 때 옮기는 쪽이 낫다. 측정한 tax는 +23~86%다(3.11).
   - 예외는 노드 용량이 1초 단위로 외부에서 줄 때다(3.9). 그런 사건이 agent RL cluster에 있다는 근거는 약하다.
4. **CXL이 설 자리는 "이전 상태는 CXL에, 무거운 명령의 새 메모리는 그 노드 DRAM에"다(3.12, 실측).**
   - bud05에서 무거운 명령 15개(Java, Ruby, C++, Go, Rust, JS, C)를 쟀다. 이전 명령이 남긴 상태를 CXL에 두고 명령만 DRAM에 묶으면 명령 시간이 +2.0% 늘었다(명령 CPU로 가중, CPU 시간으로는 +0.2%). 전부 CXL이면 +56%(CPU 시간 +84%)다.
   - 무거운 명령의 메모리 traffic은 대부분 새로 잡는 메모리(heap, compile 중간물, 빌드 결과)로 간다. 이전 상태(중앙값 59 MiB, 최대 422 MiB)는 CXL에서 읽어도 싸다.
5. **CXL 없는 대안이 강하다. 100 Gb/s로 멈추고 복사하기다(3.11).**
   - CPU 가중으로 경계 배치 이득의 97%를 얻고, 노드 수도 거의 같다. mini-SWE-agent처럼 명령마다 새 shell을 띄우면 명령 사이 상태가 작다(중앙값 약 130 MiB).
   - CXL 쪽 장점은 다음과 같다.
     - tail: 무거운 명령 p99 회수가 80~83%로, 복사의 65~68%보다 높다.
     - 25 GbE: 복사는 tail이 무너지지만 CXL은 상관없다.
     - 출발 노드 CPU와 목적지 메모리를 쓰지 않는다.
     - 쉬는 sandbox 메모리를 DRAM에서 뺀다.
   - 이 차이가 논문을 지탱할 만큼 큰지는 아직 열려 있다.
6. **이 이야기에서 hand-off 메커니즘이 받는 요구는 "10 ms 안에 아무 노드에나 붙기"다.**
   - 10 ms와 1 ms는 결과가 같다(3.7). lab hand-off는 실제 SWE 작업에서 1.3~2.7 ms였다.
   - M4에 가장 가까운 lab `snapshot` 모드도 재개 ACK까지 8.5 ms다. 옮긴 뒤 EPT를 다시 채우는 비용에 따라 M4도 이 안에 들 수 있다. 이 비교(M4, M4+P)가 다음에 잴 것이다.
7. **약하거나 버린 시나리오**
   - Python RL: 명령 폭이 좁아 노드 안에서 섞인다.
   - 동기 step: 흩어 배치하면 충분하다.
   - 같은 task 묶음: 모을 이유가 있을 때만 선다.
   - 오래 사는 session의 대피: 가치는 CXL 공유 메모리에 있고 ms는 필요 없다.

### S1. 명령 단위 CPU 배분을 노드 밖으로 넓히기

**상황.** 업계는 이미 명령 단위로 CPU를 나눈다. ARL-Tangram(Xiaomi MiMo 학습에 사용)은 `docker exec` 직전에 cgroup cpuset을 키우고 명령이 끝나면 회수한다. test는 `pytest -n`으로 1~32코어를 준다. 고정 폭보다 명령 완료 시간이 2~3배 짧고, step은 최대 1.5배 빠르다.

**막힌 곳.** 상태가 노드 메모리에 있어서 "같은 trajectory의 이후 명령은 처음 고른 노드에서만 돈다". 노드를 고를 때 trajectory 전체 메모리를 그 노드에 잡아야 한다. 논문은 노드가 128코어 이상이라 조각남이 심하지 않다고 보고, 노드 사이 이동은 다루지 않는다. batch 1536에서 대기가 실행 시간의 35%까지 오른다(1280에서는 1.5%). 다만 이 대기가 노드 고정 때문인지는 나누지 않았다.

**hand-off가 하는 일.** 상태를 CXL에 두면 명령마다 코어가 남는 노드로 넘길 수 있다. 노드 범위의 배분을 cluster 범위로 넓히는 것이다. 이론 근거는 Harchol-Balter & Downey(TOCS'97)다. 한곳에 묶인 job은 배치 기회가 한 번뿐이고, 싸게 옮길 수 있으면 phase마다 다시 배치할 수 있다.

**결과.** 노드 범위 배분 대비 cluster 범위 배분의 이득과 필요한 이동 속도는 3.2·3.3·3.7절, CXL 없는 복사와의 비교는 3.11절, 이전 상태를 CXL에 둘 때의 tax는 3.12절에 있다.

### S2. 짧은 명령이 많은 workload에서 명령마다 배치

이동 비용은 옮기는 명령마다 더해진다. 그래서 명령 시작 때 옮기는 정책에 필요한 이동 속도는 CPU가 어떤 길이의 명령에 있는지가 정한다(3.1절).

- 다언어 SWE(빌드가 무거움)는 CPU의 74%가 10초 넘는 명령에 있다. 100 ms 이동으로도 CPU의 96%를 5% 이하 비용으로 옮긴다. ms가 필요 없다.
- Python RL은 CPU의 35%가 2초 미만 명령에 있다.
  - `python script.py`(run)가 CPU의 30%인데 길이 중앙값이 0.16초이고, 문자열만으로는 무거운지 알 수 없다.
  - 5% 이하 비용으로 옮길 수 있는 CPU는 1 ms에서 98%, 50 ms에서 78%, 100 ms에서 65%다.
  - snapshot 계열 최선(AgentENV 깨우기 50 ms 미만, 업체 주장)으로도 약 4분의 1이 남는다. 옮긴 뒤 page fault로 다시 채우는 비용은 여기에 넣지 않았다.

### S3. CXL 용량이 밀도를 올리면 CPU가 막힌다

- Python RL sandbox는 메모리가 밀도를 정한다.
  - 15코어의 70%를 채우려면 코어당 sandbox 17개가 필요하다. 메모리가 허락하는 밀도는 bud05 코어당 8~10개, DSec 2.7~4.2개다(11-06).
  - DSec도 "남아 있는 메모리가 cluster 용량을 직접 제한한다"고 쓴다. ARL-Tangram은 trajectory 전체 메모리를 노드에 잡는다.
- CXL로 메모리를 늘리면 밀도가 오르고 CPU 사용률이 오른다. 그때 노드 사이 경합과 명령 tail이 생기는지가 S1·S2로 이어진다.
- 결과: Python RL에서는 메모리가 막는 구간에 CPU 경합이 거의 없었다(3.4절).

### S4. network를 쓰는 무거운 명령 도중 이동 (vCPU만 이동)

- Python RL에서 install(pip 등)은 sandbox CPU의 13%, 명령 시간의 23%다(11-09). 길이는 p50 4.6초, p90 30초다.
- Nebius는 install·test·reset이 CPU, 메모리, I/O를 두고 다툰다고 보고했다. 그래서 package 설치 명령을 동시 16개로 묶었다.
- 이 명령 도중 sandbox 전체를 옮기면 TCP 연결과 host 쪽 network 상태(tap, conntrack)를 같이 넘겨야 한다.
  - 기존 재우기/깨우기는 연결을 끊는다(E2B, Modal).
  - vCPU만 옮기고 장치는 원래 host에 두면(FragVisor의 delegation), I/O는 원래 host에서 계속되고 연결도 유지된다.
- 대가도 있다.
  - I/O 부하와 장애 범위가 원래 host에 남는다.
  - I/O마다 한 번 더 건너간다. Oasis의 CXL 공유 메모리 channel은 약 600 ns다.

### S5. 예측이 틀렸거나 외부에서 용량이 줄었을 때 회복하기 (실행 중 이동)

- **예측 실패.**
  - 다언어 명령을 명령 문자열 분류로 맞히면, CPU ≥ 1초인 명령에 대해 recall 0.85, precision 0.78이다(simulator 입력).
  - 무거운 명령 안에서도 폭이 변한다. 수요 p90/평균의 중앙값이 1.64다.
  - Harchol-Balter & Downey에서는 이름으로 예측해 배치하는 정책보다 실행 중 이동이 평균 지연을 35~50% 더 줄였다. 배치가 틀리면 되돌릴 수 없기 때문이다.
  - 우리 simulator에서는 실행 중 이동이 명령 시작 때 옮기기에 6~14%p만 더했다(3.2절). 무거운 명령은 명령 문자열로 거의 다 알아본다(무거운 CPU의 98%). 남은 손실은 예측 실패보다 시작 뒤에 들어온 다른 명령과 폭 변화에서 온다.
- **외부 용량 감소.**
  - 같은 host의 다른 tenant, GC, harvest 회수는 sandbox 자신의 명령으로 예측할 수 없다.
  - Prequal(YouTube): 1분 평균으로는 한도 안이지만 1초 단위로는 2배 넘게 튀었다.
  - Nu: 이런 경우 100 µs 이동으로 방해 시간이 15배 짧아졌다.
  - Fly.io는 noisy neighbor 때문에 CPU quota를 도입했다.
- 우리 측정에는 외부 tenant가 없다. 근거는 문헌과, 가정한 사건 모양에 대한 simulator 민감도(3.9절)뿐이다.

### S6. 오래 사는 상태 있는 session의 정리와 대피

- **실제 운영 사례: Sail Research(2026-07).**
  - host가 뜨거워지면 VM을 옮기고, 회수 경고 안에 host를 비운다.
  - 정지는 몇 초이고 하루 몇 번 이하다.
  - VM은 64~128 GB, agent는 몇 주 살고 대부분 잠들어 있다. post-copy로 2 MB씩 가져온다.
- session은 점점 길어진다. Cursor는 몇 시간~몇 주, Devin은 단계 사이 며칠, AgentCore는 8시간이다.
- 대안의 문제: 재우기/깨우기는 연결을 끊고, 큰 VM은 복사가 길다.
- CXL에 메모리를 두면 복사가 없고, hand-off는 장치 상태까지 이어 간다.
- 다만 이 용도는 ms가 필요 없다. M3/M4 수준이면 충분하다. 이 시나리오의 가치는 CXL 공유 메모리에 있고, hand-off 속도에는 없다.

### S7. 같은 task 묶음의 상관된 burst

- GRPO group은 같은 task를 G번 동시에 시작한다.
  - 같은 test를 비슷한 시각에 돌린다.
  - image locality 때문에 한 노드에 묶어 두기 쉽다.
- 11-05 측정에서 같은 trace 사본이 함께 시작하면 손실이 3배 넘게 커졌고, 경합 episode가 길어졌다(손실 가중 p50 16.5초).
- GKE는 많은 agent가 한꺼번에 깨어나는 "thundering herd"를 위험으로 꼽는다.
- 다른 노드가 비어 있어야 옮길 곳이 있다. 그래서 cluster를 여러 job이 같이 쓰는 경우에 해당한다.
- simulator 결과는 3.8절에 있다. 처음부터 흩어 놓으면 이동 없이도 같은 step p99를 얻는다.

### 3.2 명령 시작 때 옮기기 대 실행 중 hand-off

simulator 결과다([boundary-vs-handoff-20261113](../boundary-vs-handoff-20261113/README.md), Codex가 구현하고 돌렸다).

**설정**
- 다언어 264 trace를 재생했다. 명령 폭은 30코어로 제한했다.
- 16노드 × 48/96/192코어, seed 2개다.
- 새 sandbox는 power-of-2로 배치한다.

**정책**
- 경계 배치: 무거운 명령(CPU ≥ 1초)이 시작할 때 한 번 판단한다. 현재 노드에 그 폭의 자리가 없으면 자리가 가장 많은 노드로 옮기고, 그동안 명령이 L만큼 멈춘다.
  - oracle은 무거운지와 평균 폭을 안다.
  - class는 명령 문자열로 test/build/install을 고르고, 폭은 같은 repo의 다른 trace에서 가져온다.
- reactive: 실행 중에 50 ms 동안 넘치면 10 ms hand-off로 옮긴다.
- migration: 기존 pre-copy다(100 Gb/s, 판단 500 ms).

**지표.** 아무것도 안 할 때(none)와 이상적 공유(pool) 사이의 이득 가운데 되찾은 비율이다. 칸은 CPU 가중 slowdown 기준 / 무거운 명령 p99 기준(%)이다. 목표 사용률은 90%다.

| 정책 | 48코어 | 96코어 | 192코어 |
|---|---|---|---|
| migration(pre-copy, 실행 중) | 5 / 11 | 6 / 14 | 12 / 15 |
| 경계 L = 1 s | 49 / −63 | 42 / −143 | 37 / −249 |
| 경계 L = 100 ms | 67 / 73 | 69 / 70 | 74 / 66 |
| 경계 L = 10 ms(1 ms와 같음) | 69 / 80 | 72 / 81 | 78 / 83 |
| 경계 class L = 1 ms | 68 / 74 | 71 / 77 | 77 / 79 |
| reactive 10 ms | 75 / 86 | 75 / 85 | 80 / 85 |
| 경계 1 ms + reactive | 76 / 89 | 77 / 88 | 82 / 87 |

**경계 배치가 이득의 대부분을 가져간다(약 70~78%).**
- 명령 문자열 분류로도 oracle과 1~2%p 차이다.
- 다만 이동은 명령이 이미 도착한 뒤라 명령 시간에 그대로 더해진다.
  - 10 ms 이하면 1 ms와 같다.
  - 100 ms면 CPU 가중으로는 거의 같고, tail에서 7~17%p를 잃는다.
  - 1초면 CPU 가중은 절반만 되찾고, tail은 아무것도 안 할 때보다 나빠진다.

**경계 배치 뒤 남은 손실은 실행 중에 생긴다.** 남은 손실의 91~99%는 시작할 때 자리가 있던 무거운 명령에서 나왔다. 그 뒤 같은 노드에 다른 명령이 들어오거나, 명령 자신의 폭이 커졌다. 무거운 명령 안에서 수요 p90/평균의 중앙값은 1.64다.
- 이 부분은 실행 중 이동만 고친다.
- reactive를 더하면 6~14%p를 더 되찾는다.

**기존 migration은 실행 중 이동으로 거의 못 되찾는다.** 5~12%다. 실행 중 상태가 크고(3.6절), 판단과 이동이 느리다.

### 3.3 같은 tail에서 필요한 노드 수

목표 사용률을 70~95%로 바꿔 가며 SLO를 지키는 최대 실제 사용률을 찾았다. 이것으로 아무것도 안 할 때 대비 노드 절감을 계산했다.

- 칸은 "최대 사용률 / 노드 절감"이다.
- `≥`는 측정한 최고점까지 통과했다는 뜻이다. 이때 절감은 하한이다.
- `<`는 측정한 최저점에서도 실패했다는 뜻이다.

| CPU 가중 ≤ 1.10 | 96 | 78.6% | 79.6% / 1% | 86.0% / 9% | 92.9% / 15% | ≥ 93.3% / ≥ 16% | ≥ 93.4% / ≥ 16% | ≥ 93.4% / ≥ 16% | ≥ 94.6% / ≥ 17% |
| CPU 가중 ≤ 1.10 | 192 | 87.7% | ≥ 88.4% / 1% | 91.6% / 4% | ≥ 94.2% / ≥ 7% | ≥ 94.3% / ≥ 7% | ≥ 94.3% / ≥ 7% | ≥ 94.3% / ≥ 7% | ≥ 95.1% / ≥ 8% |
| 무거운 p99 ≤ 1.5 | 48 | 52.8% | < 77.5% | 실패 | 83.8% / 37% | 88.7% / 40% | 91.6% / 42% | ≥ 91.8% / ≥ 42% | ≥ 93.5% / ≥ 44% |

이 표에서 읽을 것은 세 가지다.

**노드가 작을수록 이득이 크다.**
- 48코어에서는 같은 CPU 가중 SLO에 노드가 26~29% 덜 든다.
- 192코어에서는 7% 이상이다. 노드가 크면 노드 안에서 이미 burst가 섞인다.
- 명령 폭 상한(30코어)과 노드 크기의 비가 중요하다. 256코어 노드 결과는 3.10절에 있다.

**명령 시작 때 옮기는 메커니즘은 100 ms 안이어야 한다.**
- 100 ms와 1~10 ms의 차이는 작다(48코어 tail SLO에서 3%p).
- 1초면 tail SLO에서 노드가 오히려 더 든다.
- 기존 pre-copy migration은 거의 이득이 없다.

**실행 중 이동(reactive)이 더하는 몫은 작은 노드에서만 보인다.**
- 48코어에서는 경계 배치 대비 노드 2~7%p다.
- 96코어 이상에서는 측정 범위 안에서 차이가 보이지 않는다.

동기 RL step(192코어, batch 16 × group 8, 사용률 75%)에서 step p99는 이렇다.
- 아무것도 안 할 때: 1.082
- 경계 배치: 1.023
- reactive: 1.020
- pool: 1.013

모두 작다.

### 3.4 Python RL 밀도와 경합

iter2 serving 기록의 LLM 간격 그대로(gap 1)에서는 Python RL sandbox가 CPU를 거의 쓰지 않는다.
- 192코어에서 실제 사용률 35%를 얻으려면 코어당 sandbox 23개(5.1 GiB/코어)가 필요하다. VM 평균 228 MiB로 계산했다.
- bud05 기준(4 GB/코어)으로는 사용률이 약 28%에 그친다.
- CXL로 메모리를 두 배 넘게 늘려야(9.1 GiB/코어) 63%다.

이 구간의 900초 측정에서는 경합이 거의 없었다. 48코어, 목표 90%에서 아무것도 안 해도 CPU 가중 1.007이다.
- 4,500초 측정은 pool도 1.188로 느렸다.
- 3,600초 ramp에서는 아무것도 안 할 때 1.055로 달랐다.
- 시작 조건에 민감하다. 그래서 이 구간에서 최대 사용률은 정하지 않는다.

LLM이 4배 빠르면(gap 0.25) 메모리가 막기 전에 CPU가 찬다. 코어당 sandbox 11개(2.5 GiB/코어)로 사용률 90%다. 48코어, 목표 90%의 결과는 다음과 같다.

| 정책 | CPU 가중 | 무거운 명령 p99 | 전체 명령 p99 |
|---|---|---|---|
| none | 1.050 | 1.43 | 1.48 |
| 경계 1 ms | 1.008 | 1.04 | 1.14 |
| 경계 100 ms | 1.011 | 1.11 | 1.14 |
| reactive 10 ms | 1.013 | 1.09 | 1.19 |
| pool | 1.000 | 1.00 | 1.00 |

- 192코어에서는 아무것도 안 해도 1.008이다.
- Python RL 명령은 폭이 좁아서(1 vCPU, 또는 8 vCPU라도 병렬이 작음) 노드 안에서 잘 섞인다.
- 여기서는 경계 1 ms가 100 ms보다 tail이 낫다(1.04 대 1.11). 명령이 짧아 지연이 바로 보인다.
- 다만 출발점(1.43)이 작아 운영자가 볼 차이는 아니다.

**판정: S3(CXL 용량으로 밀도를 올리면 CPU가 막힌다)는 Python RL에서 약하다.** 메모리가 막는 구간에서는 CPU 경합이 없다. CPU가 차는 구간(빠른 LLM)에서는 메모리가 막지 않는다.

### 3.5 LLM 대기 동안 미리 옮기기 (리뷰어 반론 Q3)

[premove.json](premove.json), `premove.py`. 다언어 264 trace다. 대기 시간은 기록된 LLM 간격이다(Gemini 3.5 Flash). 명령 종류는 11-12 `cmdkind`로 정했다.

**대기가 짧다.**
- 무거운 명령 앞의 대기는 p10 1.24초, p50 1.87초, p90 6.8초다.
- 무거운 CPU 가운데 앞 대기가 3초 이상인 것은 29%, 10초 이상은 6%다.
- 몇 초짜리 live migration을 대기 안에 숨길 수 있는 경우는 적다.

**대기가 시작될 때는 다음 명령을 모른다.** 명령은 LLM 생성이 끝나야 나온다.

| 예측 시점과 정보 | recall | precision | CPU recall | 무겁다고 예측한 명령 비율 |
|---|---|---|---|---|
| 대기 시작, 이력(직전 종류, 직전 무거움, 앞에 무거운 명령 있음), 문턱 0.2 | 0.55 | 0.25 | 0.52 | 25% |
| 대기 시작, 같은 이력, 문턱 0.3 | 0.18 | 0.48 | 0.11 | 4% |
| 명령 시작, 명령 문자열 | 0.85 | 0.78 | 0.98 | 13% |

- 이력으로 무거운 CPU의 절반을 잡으려면 명령 4개 중 1개를 옮겨야 하고, 그 3/4이 헛이동이다.
- 무거운 명령 앞에 가장 많이 오는 것은 탐색 명령(grep, cat, ls)이다(무거운 CPU의 32%). 그런데 탐색 명령 뒤에 무거운 명령이 올 확률은 5%뿐이다.

simulator로 잰 결과(오래된 view, 헛이동 비용 포함)는 3.11절에 있다.

### 3.6 옮길 때 넘겨야 하는 상태의 크기

[boundary-state.json](boundary-state.json), `boundary_state.py`. 10-14 Docker DRAM 재생의 cgroup 100 ms 샘플을 썼다.

- **명령 시작 직전:** 마지막 샘플의 anon(익명 메모리), file(page cache), 그때까지의 블록 쓰기 누적(쓰기 layer 크기의 상한)이다.
- **실행 중:** 무거운 명령 안의 샘플이다.
- 둘 다 CPU 가중이다.
- container 값이라 VM의 guest kernel은 빠져 있다.

| 시점 | anon p50 / p90 | anon + file + 쓰기 p50 / p90 / p99 | 100 Gb/s로 멈추고 복사해 100 ms 안 | 25 Gb/s로 100 ms 안 |
|---|---|---|---|---|
| 무거운 명령 시작 직전 | 1.4 MiB / 985 MiB | 약 130 MiB / 약 2 GiB / 약 5 GiB | 무거운 CPU의 85% | 60% |
| 무거운 명령 실행 중 | 772 MiB / 3.1 GiB | 1.4 GiB / 4.7 GiB / 11.8 GiB | 44% | 15% |

**명령 사이의 상태는 작다.**
- mini-SWE-agent는 명령마다 새 shell을 띄워서, 명령 사이에는 process가 거의 남지 않는다. 남는 것은 파일과 page cache다.
- 그래서 100 GbE에서는 CXL 없이 멈추고 복사해도, 명령 시작 때 옮기기가 대부분 100 ms 안에 끝난다.
  - 꼬리는 남는다. p90 상태 2 GiB는 100 Gb/s에서 160 ms, 25 Gb/s에서 640 ms다.
  - 목적지에는 그만큼 빈 메모리가 있어야 한다.
- persistent shell, Jupyter kernel, 띄워 둔 dev server나 DB를 쓰는 agent(OpenHands, SWE-agent, 사람의 개발 환경)는 명령 사이 상태가 더 크다. 우리 자료로는 아직 잴 수 없다.

**실행 중 상태는 10배 크고 계속 바뀐다.**
- 복사로 옮기면 100 Gb/s에서도 100 ms 안에 들어오는 몫이 44%다.
- pre-copy는 쓰기가 많으면 수렴하지 않는다.
- 실행 중 이동은 메모리를 옮기지 않는 방식(CXL hand-off, vCPU만 이동)만 ms로 할 수 있다.

simulator로 잰 결과(명령마다 복사 시간을 정지로 넣은 경계 배치)는 3.11절에 있다.

| Python RL 8 vCPU 48코어(gap 0.25) | reactive | 53 / 61 | 53 / 62 | 45 / 57 | 28 / 31 | −1 / −85 | −16 / −301 |
| Python RL 8 vCPU 48코어(gap 0.25) | 경계 1 ms + reactive | 74 / 82 | – | 68 / 76 | – | 54 / −54 | – |

기존 pre-copy migration은 실제 이동 완료까지 평균 6.8~7.7초(다언어), 1.5초(Python RL)였다. 회수율은 다언어 6~12%, Python RL −14%다.

**실행 중 이동은 10 ms 안이어야 한다.**
- 100 ms면 이득이 절반 남짓으로 줄고, 300 ms부터는 아무것도 안 할 때보다 나쁘다.
- 경계 배치는 100 ms까지 견딘다. 실행 중 이동은 명령 하나에 여러 번 일어나고, 판단(50 ms)과 hold 동안 노드가 계속 넘치기 때문이다.

**1 ms와 10 ms의 차이는 작다.**
- reactive에서 3~4%p다.
- 500 µs in-place 변형(D7)이 10 ms hand-off보다 더 얻는 몫은 이 정도다.

**짧은 명령 workload(Python RL)에서는 경계 배치가 reactive보다 낫다(68 대 53).**
- 명령이 짧아 판단 50 ms를 기다리는 동안 명령의 상당 부분이 지나간다.
- 둘을 합치면 74%다.

### 3.8 같은 task 묶음을 한 노드에 모을 때

simulator 결과다(Codex 11 B, [6.2절](../boundary-vs-handoff-20261113/README.md)).

**설정**
- 같은 trace 사본 G = 8개를 한 group으로 동시에 시작한다.
  - 실제 rollout은 같은 task라도 서로 다르다. 그래서 이것은 강한 상관을 가정한 검사다.
  - Python RL 자료에는 실제 G = 8 묶음이 없었다.
- 16노드 × 192코어다. 같은 sandbox 밀도에서 group을 한 노드에 모으거나(pack) 노드마다 흩는다(spread).
- 칸은 동기 step p99다(가장 늦은 rollout 기준). 목표 사용률은 80%다.

| 작업량 | spread, none | pack, none | pack, 경계 1 ms | pack, reactive 10 ms | pack, 경계 + reactive | pool |
|---|---|---|---|---|---|---|
| 다언어 | 1.076 | 1.488 | 1.076 | 1.056 | 1.050 | 1.037 |
| Python RL 8 vCPU | 1.000 | 1.010 | 1.002 | 1.004 | 1.002 | 1.000 |

**다언어 group을 한 노드에 모으면 step p99가 1.49배가 된다.** 같은 test를 동시에 돌려서다.
- 명령 시작 때 옮기기만으로 흩어 놓은 것과 같아진다(1.076).
- 실행 중 이동을 더하면 그보다 조금 낫다(1.050).

**그런데 처음부터 흩어 놓으면 이동 없이 1.076이다.**
- 그래서 이 시나리오는 모을 이유가 있을 때만 선다.
  - 예: 같은 image의 page cache를 노드에서 나눠 쓰기(image 배치 chunk 분석, 11-09).
- simulator에는 모아서 얻는 이득과 옮겨서 잃는 locality가 없다.

**Python RL은 차이가 없다(1.010).**

### 3.9 외부에서 노드 용량이 줄 때

simulator 결과다(Codex 11 C, [6.3절](../boundary-vs-handoff-20261113/README.md)).

**설정**
- 노드마다 용량 감소 사건을 독립 Poisson으로 넣었다.
  - 사건 동안 코어가 a만큼 줄고, 평균 길이는 T다.
  - 전체 시간 중 사건 비율(duty)은 5% 또는 20%다.
- 정책은 미래 사건을 모른다.
- **실제 측정한 사건이 아니라 가정한 모양에 대한 민감도다.**
- 칸은 사건이 더한 손실 중 되찾은 비율(%)이다.

| 작업량 | a, duty | T | 경계 1 ms | reactive 10 ms | reactive 1 s | 경계 + reactive |
|---|---|---|---|---|---|---|
| 다언어 192코어, 80% | 50%, 20% | 1 s | 37 | 61 | −57 | 63 |
| 다언어 192코어, 80% | 50%, 20% | 10 s | 73 | 83 | 16 | 84 |
| 다언어 192코어, 80% | 50%, 20% | 60 s | 86 | 87 | 45 | 88 |
| 다언어 192코어, 80% | 25%, 5% | 1 s | 54 | 77 | −95 | 79 |
| Python RL 48코어, 90% | 50%, 20% | 1 s | 39 | 29 | 8 | 44 |
| Python RL 48코어, 90% | 50%, 20% | 10 s | 54 | 41 | 20 | 57 |
| Python RL 48코어, 90% | 50%, 20% | 60 s | 60 | 53 | 31 | 61 |

다언어 a = 50%, T = 10 s, duty 20%의 절대값은 다음과 같다.

| 정책 | CPU 가중 | 무거운 명령 p99 |
|---|---|---|
| none | 1.220 | 3.01 |
| 경계 1 ms | 1.053 | 1.38 |
| reactive 10 ms | 1.032 | 1.23 |
| 경계 + reactive | 1.029 | 1.19 |
| pool | 1.006 | 1.10 |

**실행 중 이동이 경계 배치보다 확실히 나은 곳은 여기뿐이다.**
- 사건이 명령보다 짧으면(T = 1 s) 차이가 크다. 다언어에서 reactive가 경계 배치보다 17~33%p 더 되찾는다(a, duty 네 조합).
- 사건이 길면(60 s) 다음 명령 시작 때 옮겨도 되므로 차이가 없다.
- 1초 이동(빠른 live migration 수준)은 T ≤ 10 s 사건에서 거의 못 되찾거나 오히려 해롭다.

**Python RL에서는 경계 배치가 더 낫다.** 명령이 짧아 다음 명령 시작이 금방 온다.

**이런 사건이 agent RL cluster에 실제로 있는지는 근거가 약하다.**
- 11-09 공개 RL job 분석에서 sandbox 밖 CPU 작업(reward·test)은 작고 퍼져 있었다.
- GPU 노드 harvest 시험에서는 GPU 작업이 코어를 계속 써서, 용량이 바뀔 틈이 없었다.
- 문헌의 사례는 다른 tenant가 있는 공유 cloud다. Prequal에서는 1분 평균이 한도 안인데 1초 단위로 2배를 넘었다. Nu에서는 CPU가 갑자기 절반이 되는 사례를 다뤘다.
- 그래서 S5b는 "여러 고객을 받는 sandbox 플랫폼"의 시나리오다. RL 전용 cluster의 시나리오는 아니다.

### 3.11 미리 옮기기, network 복사, CXL tax 손익분기

simulator 결과다(Codex 12, [7절](../boundary-vs-handoff-20261113/README.md)). 다언어 cap30, 16노드, seed 2개다. 칸은 pool 이득 중 되찾은 비율(CPU 가중 / 무거운 명령 p99, %)이고 목표 사용률은 90%다.

| 정책 | 48코어 | 96코어 | 192코어 |
|---|---|---|---|
| LLM 대기 중 미리 옮기기, 이력 예측, L = 1 s | 39 / 46 | 40 / 48 | 45 / 49 |
| 같은 것, 다음 명령을 아는 oracle | 52 / 61 | 52 / 60 | 56 / 60 |
| 같은 것, oracle, L = 3 s | 31 / −65 | 14 / −164 | −16 / −329 |
| 미리 옮기기(이력, 1 s) + 명령 시작 때 경계 1 ms | 59 / 71 | 62 / 72 | 69 / 73 |
| 명령 시작 때 경계, 명령 문자열 분류, 1 ms | 68 / 74 | 71 / 77 | 77 / 79 |
| 명령 시작 때 100 Gb/s로 멈추고 복사 | 67 / 68 | 70 / 66 | 75 / 65 |
| 명령 시작 때 25 Gb/s로 멈추고 복사 | 63 / 17 | 63 / 5 | 67 / −28 |
| 명령 시작 때 경계, oracle, 1 ms | 69 / 80 | 72 / 81 | 77 / 83 |

CPU 가중 slowdown ≤ 1.10에서 아무것도 안 할 때 대비 노드 절감은 다음과 같다.

| 정책 | 48코어 | 96코어 |
|---|---|---|
| 미리 옮기기(이력, 1 s) | 13% | 8% |
| 미리 옮기기 + 경계 1 ms | 23% | 13% |
| 100 Gb/s 복사 | 26% | 15% |
| 25 Gb/s 복사 | 24% | 14% |
| 경계 1~10 ms | 26% | ≥ 16% |

무거운 명령 p99 ≤ 1.5에서는 48코어 100 Gb/s 복사가 36%, 경계 1~10 ms가 40%다. 25 Gb/s 복사와 미리 옮기기(이력)는 측정 범위에서 SLO를 지키지 못했다.

**LLM 대기 중 미리 옮기기는 명령 시작 때 옮기기보다 못하다(리뷰어 반론 Q3에 대한 답).**
- 이력 예측은 이동의 74%가 헛이동이다.
- 다음 명령을 아는 oracle도 52~56%에 그친다.
  - 옮긴 무거운 명령의 31~44%는 명령이 시작할 때 목적지에 자리가 없었다.
  - 대기 시작 때 본 부하가 명령 시작 때는 이미 바뀌어 있다.
- 3초 이동은 대기(중앙값 1.9초) 안에 숨지 못한다. 옮긴 명령의 64~70%에서 정지가 명령 시간으로 넘친다.
- 명령 시작 때 경계 배치에 미리 옮기기를 더하면 경계 배치만 할 때보다 나빠진다. 헛이동과 목적지 예약이 자리를 막는다.
- LLM 대기를 4배로 늘려도(생각이 긴 모델) 미리 옮기기는 나아지지 않는다(oracle 48%, 이력 33%). 대기가 길수록 본 부하가 더 낡는다. 경계 배치는 81%로 오른다.

**100 Gb/s로 멈추고 복사하면 CPU 가중으로는 경계 배치 이득의 97%를 얻는다.**
- 노드 수로도 거의 같다(48코어 26% 대 26%).
- 차이는 tail에 있다. 무거운 명령 p99 회수는 65~68% 대 80~83%다. 상태 큰 명령(p90 2.6 GiB, 100 Gb/s에서 226 ms)이 tail을 만든다.
- 25 Gb/s에서는 tail이 아무것도 안 할 때와 비슷하거나 나쁘다.
- 이 복사 모델은 복사 방식에 유리한 하한이다.
  - container 상태라 guest kernel과 guest page cache가 빠져 있다.
  - 동시 복사의 대역폭 나눔, 정지 중 추가 쓰기가 없다.
  - 출발 노드 CPU는 복사 시간 × 1코어만 넣었다.

**sandbox를 CXL에 둔 채 무거운 명령을 돌리면 tax가 이득을 넘는다.** 모든 sandbox를 CXL에 두고 실행 중 hand-off(reactive)를 하면서, 무거운 명령을 τ배 느리게 했다.

| 비교 | CPU 가중 손익분기 τ | 무거운 p99 손익분기 τ |
|---|---|---|
| DRAM 경계 1 ms 대비, 48코어 90% | 1.013 | 1.032 |
| DRAM 경계 1 ms 대비, 192코어 90% | 1.002 | 1.007 |
| 100 Gb/s 복사 대비, 48코어 90% | 1.017 | 1.088 |

- 무거운 명령 tax가 1~2%만 돼도 DRAM에서 경계 배치하는 쪽이 낫다.
- 측정한 tax는 +23%(10-14 서버)에서 +31~86%(bud05 DCD)다.
- τ = 1.23이면 CPU 가중 slowdown이 1.50~1.62다. 단독 실행 하한부터 1.23이라 부하 분산으로 메울 수 없다.

**결론: CXL과 hand-off가 설 자리는 "무거운 명령은 DRAM에서 돌고, 명령 시작 때 옮길 때만 CXL을 쓰는" 설계뿐이다.**
- 그러려면 이전 명령이 남긴 상태를 CXL에 둔 채 무거운 명령을 DRAM에서 돌려도 tax가 작아야 한다.
- 3.12절에서 이것을 실측했다.

### 3.12 실측: 이전 상태는 CXL에 두고 무거운 명령만 DRAM에서

3.11절의 결론대로라면 CXL은 "무거운 명령은 DRAM에서 돈다"는 조건에서만 쓸모가 있다. 그런데 sandbox를 CXL에 둔 채 명령만 DRAM에 붙이면, 명령은 이전 명령이 남긴 상태(소스, 도구, 빌드 결과의 page cache)를 CXL에서 읽는다. 그 tax를 bud05에서 쟀다([split-stages.csv](split-stages.csv), [split-summary.json](split-summary.json), 실행별 원자료 [split-runs.jsonl](split-runs.jsonl), `split_tax.py`, `split_report.py`). 명령 출력 log는 남기지 않았다.

**설정**
- 11-12 파일럿과 같은 container 방식이다.
  - 명령은 `docker exec`로 실행하고 MPOL_BIND helper로 메모리 node를 정한다.
  - 시작 전에 image 파일의 page cache를 비워, 파일 page가 처음 읽은 명령의 node에 올라가게 했다.
- 조건 세 가지다. 무거운 명령 k에 대해 명령 0..k−1을 대기 없이 재생한 뒤 2초 쉬고 k를 잰다.
  - DRAM: 앞 명령과 k 모두 node 0.
  - CXL: 앞 명령과 k 모두 node 2(DCD, 지연 661 ns, 읽기 10.3 GB/s).
  - split: 앞 명령은 node 2, k만 node 0. 앞 명령이 남긴 page는 node 2에 그대로 있고, k가 새로 잡는 메모리는 node 0에 간다.
- 무거운 명령 15개다. 각 trace의 첫 무거운 명령과, 앞에 무거운 명령이 있었던 경우(같은 test를 다시 돌리거나 build 뒤 test)를 함께 골랐다. 11-12 파일럿의 lombok·rubocop 단계와, 10-14 재생에서 timeout 없이 끝난 다른 언어 trace에서 골랐다.
- (명령, 조건)마다 새 container로 3번 돌렸고, 반복마다 순서를 섞었다. 모두 135번, 42분이다.
- CPU는 2-31(NUMA 0), 측정 process는 CPU 0-1이다. 다른 작업이 없을 때 돌렸다(Codex simulator가 끝난 뒤).
- 135번 모두 종료 코드가 원본과 같았고 timeout은 없었다.
- `memory.numa_stat`으로 배치를 확인했다.
  - DRAM 조건은 node 2에 page가 없었다.
  - CXL 조건은 k가 node 0에 page를 더하지 않았다.
  - split 조건은 k 동안 node 2의 page가 늘지 않았다.

| 시간 tax, 중앙값 | +41% | +2.1% |
| CPU 시간 tax, CPU 가중 | +84% | +0.2% |
| split 시간 tax 최대 | – | +11%(gson 4) |

DRAM 3번 사이의 흔들림((최대 − 최소) ÷ 중앙값)은 중앙값 1.5%였다.

**이전 상태를 CXL에 둔 채 무거운 명령을 DRAM에서 돌리면 tax가 거의 없다.**
- 시간으로 +2% 안팎, CPU 시간으로는 +0.2%다. 전부 CXL에 둔 +56%(CPU 시간 +84%)와 크게 다르다.
- 앞에 무거운 명령이 있었던 7개(lombok 23·36, gson 13, fmt 16, preact 20, rubocop 26·42)는 도구와 소스가 이미 CXL에 올라가 있다. 이전 상태가 50~422 MiB인데도 시간 tax는 −0.1~+4.7%였다.
- 가장 큰 gson 4(+11%)는 CPU 시간이 DRAM과 같았다(27.8 대 27.7초). CPU 밖에서 기다린 시간이고, CXL에 있던 이전 상태도 3 MiB뿐이다. Maven의 network 접근 같은 흔들림으로 본다. DRAM 3번도 11% 흔들렸다.
- 무거운 명령의 메모리 traffic은 대부분 새로 잡는 메모리(JVM heap, compiler 작업 메모리, 빌드 결과)로 간다는 뜻이다. CXL에 남은 이전 상태는 한 번 읽히고 끝난다.

**명령이 끝난 뒤 DRAM에 남는 것**
- 명령 process가 끝나면 anon 메모리는 반납된다(명령마다 새 shell).
- 남는 것은 새로 쓰거나 처음 읽은 파일의 page cache다. 중앙값 16 MiB, 최대 1.6 GB(cargo test의 target), 580 MiB(go build cache), 353 MiB(npm)였다.
- 다른 노드로 옮기기 전에는 이것을 CXL로 내려야 한다. 10 GB/s면 1.6 GB가 약 0.16초다. 무거운 명령 앞 LLM 대기의 p10(1.24초)보다 짧다. DCD의 쓰기 대역폭은 아직 재지 않았다.

**한계**
- container 대리 측정이다. VM에서 같은 배치를 하려면 guest가 "CXL 층"과 "붙은 노드의 DRAM 층"을 따로 보고, 새 메모리를 DRAM 층에서 잡아야 한다. 이것은 아직 구현도 측정도 없다(4장).
- split에서 앞 명령이 읽지 않은 image 파일(도구, 의존성)은 k가 처음 읽으면서 DRAM에 올라간다. 오래 산 sandbox라면 이것도 CXL에 있을 것이다. 앞에 무거운 명령이 있었던 7개가 이 경우에 가깝다.
- 명령마다 새 shell을 띄우는 agent다. persistent shell이나 kernel이 큰 anon 상태를 들고 다시 쓰는 명령은 재지 않았다.
- 2초 쉰 뒤 시작했다. LLC는 대부분 비어 있다(11-12 파일럿 7절).
- DCD가 느린 장치라 CXL 조건의 tax가 크다. 더 빠른 CXL에서는 전부 CXL의 tax가 줄어 3.11의 손익분기가 달라질 수 있다.

## 4. 추천 이야기

**"sandbox는 CXL에 주차하고, 무거운 명령마다 코어가 남는 노드의 DRAM에서 시작한다."**

**문제**
- agent sandbox는 대부분 LLM을 기다리며 쉬고, CPU는 무거운 명령(test·build)에 몰린다.
- 업계는 이미 노드 안에서 명령마다 코어를 붙인다(ARL-Tangram). 하지만 상태가 노드 메모리에 있어서 sandbox는 처음 고른 노드를 떠나지 못한다.
- 그래서 노드 사이 불균형이 남는다. 같은 CPU 가중 SLO에서 노드가 48코어면 26%, 96코어면 16%, 192코어면 7% 이상 더 든다(3.3).
- 다음 명령은 LLM 생성이 끝나야 나오고 대기도 짧다(중앙값 1.9초). 대기 중에 미리 옮기면 명령 시작 때 옮기기보다 못하다(3.11).

**설계**
- 쉬는 sandbox는 VM 전체(메모리, EPT, vCPU 상태)를 CXL에 둔다. 11-12 측정에서 대기 중 메모리의 78~98%가 10초 넘게 쓰이지 않았다.
- 명령 문자열로 무거운 명령(test·build·install)을 알아본다. 무거운 CPU의 98%를 잡는다(3.5).
- 무거운 명령이 오면 코어가 남는 노드에 VM을 몇 ms 안에 붙인다.
  - 이전 상태는 CXL에서 그대로 읽는다.
  - 명령이 새로 잡는 메모리는 그 노드 DRAM에서 준다.
  - 이렇게 하면 tax가 +2%(CPU 시간 +0.2%)다(3.12). 전부 CXL이면 +56%다.
- 명령이 끝나면 다음 LLM 대기 동안 DRAM에 남은 새 page를 CXL로 내린다. 중앙값 16 MiB, 최대 1.6 GB였다(3.12).
- 가벼운 명령은 CXL에서 그대로 돈다(tax +1~5%, CPU의 3%).
- 실행 중에는 옮기지 않는다. 새 메모리가 붙은 노드의 DRAM에 있기 때문이다. 3장에서 실행 중 이동의 추가 이득은 작았다.

**hand-off에 요구하는 것**
- 붙이는 시간이 10 ms 안이면 tail까지 거의 다 얻는다. 100 ms면 CPU 가중은 거의 같고 무거운 명령 p99 회수가 10%p쯤 준다(3.2, 3.7).
  - 우리 lab hand-off는 실제 SWE 작업에서 1.3~2.7 ms였다(RESEARCH 3.3).
  - 10 ms 안이면 1 ms와 결과가 같다(3.7). 그래서 CXL 위 restore(M4)도 옮긴 뒤 EPT를 다시 채우는 비용까지 10 ms 안이면 같은 이득을 얻는다.
  - lab의 `snapshot` 모드(M4에 가장 가까움)는 정지→재개 ACK가 8.5 ms였다. 그 뒤 EPT를 빈 표에서 채우는 비용은 재지 않았다(M4+P도 없음).
  - 따라서 명령 시작 때 옮기기에서 hand-off가 M4보다 얼마나 나은지는 아직 모른다. 쉬던 sandbox의 working set이 작으면 차이가 작을 수 있다. 이것이 다음에 잴 것이다.
- vCPU만 옮기는 방식도 이 설계에 맞는다.
  - 장치(network, disk)는 원래 host에 두고 I/O를 위임한다. 장치 상태를 넘기지 않아도 된다.
  - 무거운 명령 동안만 다른 노드에서 vCPU를 돌린다.

**새로 필요한 설계**
- guest가 메모리를 두 층으로 본다.
  - CXL 층: 주소가 고정되고 EPT를 이어받는다.
  - DRAM 층: 붙은 노드의 DRAM이다. 명령마다 새로 붙고, 명령 뒤 비운다.
- 명령이 새 메모리를 DRAM 층에서 잡게 하고, 명령 뒤 남은 page를 CXL 층으로 옮긴다(guest 안 page 이동).
- virtio-mem 같은 기존 memory hotplug로 될지, 붙이고 비우는 데 얼마나 걸리는지 아직 모른다. 구현도 측정도 없다.

**100 GbE 복사와 비교**
- 같은 점: CPU 가중 slowdown과 노드 수가 거의 같다(3.11). 명령마다 새 shell을 띄우면 명령 사이 상태가 작기 때문이다.
- CXL 쪽이 나은 점은 다음과 같다.
  - tail: 무거운 명령 p99 회수가 80~83% 대 65~68%다.
  - 25 GbE cluster: 복사는 tail이 무너진다.
  - 출발 노드: 바쁜 노드가 복사에 CPU와 network를 쓰지 않는다.
  - 목적지: sandbox 전체 메모리를 비워 둘 필요가 없다.
  - 용량: 쉬는 sandbox 메모리가 DRAM에서 빠진다.
  - 상태 크기: persistent shell·kernel을 쓰는 agent처럼 상태가 커도 시간이 같다(재지 않음).

**정직하게 쓸 것**
- 이득은 노드가 클수록 줄어든다. 256코어 노드에서는 9.5%가 상한이다.
- 100 GbE 복사가 CPU 가중으로는 같다. CXL만의 몫은 tail과 메모리 용량이다.
- 3.12는 container 대리 측정이다.
- 실행 중 이동은 주장의 중심이 아니다.
- 명령 시작 때 옮기기는 10 ms 안이면 충분하다. hand-off의 µs~ms 속도 자체보다, 상태를 복사하지 않고 아무 노드에나 붙는다는 점이 이득의 근원이다.

**이야기가 무너지는 조건**
- VM에서 DRAM 층을 붙이고 비우는 비용이 10~100 ms를 넘는다.
- CXL 위 restore(M4)가 EPT 재구축까지 10 ms 안에 끝난다. 그러면 메커니즘으로서 hand-off의 몫이 사라진다(이야기 자체는 CXL 주차로 남는다).
- 명령 뒤 DRAM에 남은 page를 CXL로 내리는 데 LLM 대기보다 오래 걸린다.
- 이전 상태를 많이 다시 쓰는 명령(persistent kernel, 큰 in-memory DB)에서 이전 상태 읽기 tax가 커진다. 3.12의 이전 상태는 최대 422 MiB였다.
- 운영자가 192코어 이상 노드만 쓴다. 그러면 노드 절감이 7% 안팎이다.

## 5. 한계

**simulator**
- 유체 모델이다. 노드 안에서는 수요를 코어에 공평하게 나누고, cache·메모리 대역폭 간섭은 없다.
- 명령 수요는 10-14 Docker DRAM 단독 재생에서 잰 CPU 시계열이다. 폭은 30코어로 제한했다.
- seed는 2개다. 작은 차이(1~2%p)는 noise와 구별되지 않는다.
- 이동 중 출발 노드 CPU 비용은 1~2 ms로 작게 잡았다. 기존 migration과 restore의 실제 CPU 비용은 더 크다.
- 동기 step과 group 결과는 같은 trace 사본으로 만든 것이라 상관을 크게 잡았다.
- 외부 용량 감소는 가정한 사건 모양이다(3.9).

**상태 크기와 tax**
- 상태 크기(3.6)는 container 값이다. VM의 guest kernel, guest page cache, 장치 상태는 빠져 있다.
- 명령마다 새 shell을 띄우는 mini-SWE-agent만 봤다. persistent shell, Jupyter kernel, dev server를 쓰는 agent는 명령 사이 상태가 더 크다.
- tax는 bud05의 DCD(지연 661 ns, 읽기 10.3 GB/s) 값이다. 실제 CXL 장치는 이보다 빠를 수 있고, 그러면 실행 중 이동의 손익이 달라진다(3.11).

**외부 자료**
- 업체 주장(AgentENV, Morph, Blaxel, Unikraft의 깨우기 시간, mashines.dev의 "0 ms" 이동)은 검증하지 않았다.
- ARL-Tangram은 대기 시간 증가(batch 1536에서 실행 시간의 35%)를 노드 고정 때문이라고 나누지 않았다.
- Sail Research는 블로그 글이다. 이동 빈도와 정지 시간 외의 수치는 없다.

**명령 길이(3.1)**
- 단독 재생 값이다. 1 vCPU 재생에서는 명령이 늘어나 있다.
- 옮긴 뒤 다시 채우는 비용(page fault, EPT)은 3.1절의 이동 비용에 넣지 않았다. snapshot 계열에 불리한 요소인데 빠져 있다.
