# microVM 시스템 자원 경합: 32코어 kernel 하나, 부하 6가지 (2026-11-06)

[pool 이동 실측](../pool-mover-20261105/README.md)은 CPU 경합만 봤다. 여기서는 CPU 밖 자원을 본다. host kernel과 VMM이 하는 일(VM exit 처리, 장치 에뮬레이션, 디스크, journal, kernel lock)이 sandbox 수에 따라 얼마나 비싸지는지, 그리고 노드마다 다르게 쌓이는지다. Docker가 아니라 Firecracker microVM으로 쟀다. 같은 날 Docker로 잰 LLC 결과도 6절에 함께 둔다.

## 0. 결론

1. **kernel 하나에 VM을 늘려도 이벤트당 시스템 비용은 거의 그대로다.** 32코어에 동시 VM을 32개에서 192개로 늘렸다(10분 동안 413개 생성·종료). 비용 변화는 다음과 같다.
   - non-HLT exit 처리: 1.45 → 1.55 µs
   - virtio 알림(EPT misconfig): 4.1 → 4.2 µs
   - VMM의 디스크 syscall: 2~15 µs로 그대로
   - VM 부팅: 0.28 → 0.29초
2. **크게 오른 값은 guest가 기다리지 않는 경로에 있다.**
   - 블록 요청 latency: 0.32 → 11.8 ms(37배)
   - ext4 journal commit: 5.7 → 12.6 ms
   - host 전체 lock 대기: 2.4 → 17.9 ms/s. TAP 생성·삭제의 `rtnl_lock`과 VM 종료의 `rcu_barrier`가 대부분이다.

   Firecracker는 guest의 flush를 fsync로 넘기지 않고, VMM의 쓰기는 host page cache에서 끝난다. 디스크는 평균 42 MB/s, 장치가 바빴던 시간은 중앙값 6%라 대역폭이 모자라지도 않았다.
3. **명령이 느려진 원인은 디스크도 시스템 시간도 아니고 CPU 쪽이다.** 동시 192개, LLM 대기 ×0.25에서 명령 시간은 중앙값 1.10배다(trace 단위 1.08배, 시간 가중 1.03배). 원인별로 나누면 다음과 같다.
   - clock: 바쁜 코어가 1.6개에서 10.9개로 늘어 4085 → 3900 MHz(+4.7%)
   - vCPU의 CPU 대기: 0.9%
   - VMM thread의 CPU 대기: wakeup당 2 → 26 µs, 명령 시간의 최대 2%

   이 셋만으로 trace 단위 1.065배가 예측된다. 근거가 하나 더 있다. LLM 대기 ×1에서는 동시 VM이 똑같이 192개여도 바쁜 코어가 2개뿐이고, 명령은 1.01배다. VM 수 자체는 명령을 늦추지 않는다.
4. **task별 시스템 부하는 CPU를 따라간다.**
   - task별 시스템 시간(exit 처리 + VMM syscall + lock 대기)과 vCPU 사용의 순위 상관은 0.71이다.
   - 부하 수준이 바뀌어도 같은 task가 무겁다. K=32와 K=192에서 같은 task의 순위 상관은 exit 0.82, guest 쓰기 0.98이다.
   - 예외는 디스크를 많이 쓰는 task 3개(tsdat, cf-python, vyper)다. 시스템 시간이 CPU로 예측한 값의 1.5~2.5배다. 그래도 가장 무거운 task가 VM당 14 ms/s, 즉 코어 1.4%다.
   - lock 대기와 VMM의 CPU 대기는 task와 무관하게 host 부하를 따라 모든 VM에 고르게 붙는다.
5. **노드 사이 불균형은 시스템 쪽이 조금 크지만, 쓸 곳이 없다.** 독립 노드 3개를 겹치면 동시 192개에서 순간 불균형 몫(excess)은 CPU 7.1%, 시스템 11.2%다. 시스템 부하의 노드 간 순위 상관은 0.08로, 노드마다 따로 움직인다. 그러나 어떤 노드에서도 시스템 자원이 포화되지 않았다. 그래서 옮겨서 풀 경합이 없다.
6. **motivation으로 보면 CPU 밖 자원에서 따로 생기는 기회는 없다.**
   - LLC와 메모리 대역폭(6절)도, kernel·VMM 경로도 CPU보다 먼저 막히지 않는다.
   - Python RL microVM은 ×0.25에서 VM당 0.057코어를 쓴다. 32코어를 채우려면 동시 VM이 약 560개 필요하다.
   - 그 밀도에서 먼저 커질 후보는 VM 생성·종료 비용(`rtnl_lock`, `rcu_barrier`)이다. 이번 측정은 그 비용이 명령 경로에 오지 않는다는 것만 보였다. 생성·종료에 걸린 시간 자체는 재지 않았다(TAP 생성은 부팅 시각 기록 전에 끝난다).

## 1. 방법

| 항목 | 설정 |
|---|---|
| 노드 | bud05 CPU 0-31(NUMA 0 전체)을 노드 하나로 쓴다. vCPU thread와 VMM thread가 모두 여기서 돈다(`--sibling-offset 0`). harness는 SMT sibling 64-66, sampler와 bpftrace는 67. NUMA 1은 쓰지 않는다. governor `performance`, turbo 켜짐 |
| VM | Firecracker, vCPU 1, 메모리 2 GiB + balloon. 디스크 3개(base 읽기 전용, job, upper ext4). TAP + NAT |
| workload | `candidates-plan.json`의 Python RL 51 task, 408 trace. 닫힌 loop라 VM이 끝나면 새 VM이 들어온다. ramp 60초 뒤 10분을 잰다 |
| LLM 대기 | token 모델(6.156초 + output token당 0.02898초)에 배율 ×0.25(바쁨) 또는 ×1을 곱한다 |
| 조건 | ×0.25에서 동시 32, 64, 128, 192개(코어당 1~6개). ×1에서 96, 192개. 조건마다 seed 3개(trace 순서가 다름), 모두 18회 |
| 시스템 계측 | `experiments/contention/system.bt`(bpftrace, 2초 단위). VM별 exit 종류별 횟수와 처리 시간, VMM thread의 syscall 횟수·시간·바이트, VMM thread가 깨어난 뒤 CPU를 받기까지의 대기, kernel lock 대기(lock 주소로 짝을 맞추고 1초 넘는 값은 버림)와 호출 위치, jbd2 commit, 블록 요청 latency |
| 다른 계측 | vCPU run·wait(10 ms), turbostat, host PSI·디스크 counter, guest의 디스크 sector |
| 명령 비교 | (trace, 명령 번호)마다 중앙값을 K=32 ×0.25(seed 3개 합침)와 비교한다. 기준이 0.02초 이상인 명령만 쓴다 |
| 노드 겹침 | 독립 실행은 kernel을 따로 쓴다. 같은 조건의 실행 3개를 ramp 끝 기준으로 맞춰, 노드 3개짜리 cluster로 본다(`system_report.py --overlay`) |


## 3. 명령이 느려진 원인 (192개, ×0.25)

K=32와 K=192에서 공통 명령이 5개 이상인 trace 97개를 썼다. 각 trace의 시간 비율과, 그 trace가 낮은 부하에서 명령 1초당 쓴 vCPU 시간과 VMM wakeup 수를 맞대었다.

| 항목 | 값 |
|---|---|
| 측정한 비율 | trace 중앙값 1.082, 시간 가중 1.030 |
| clock | 4085 → 3900 MHz, CPU 일에 ×1.047 |
| vCPU 대기 | vCPU 시간의 0.86% |
| VMM wakeup 대기 | wakeup당 +23.9 µs. 명령 1초당 VMM 대기는 낮은 부하 0.09%, 높은 부하 2.02%(VM 수명 전체를 명령 시간으로 나눈 상한) |
| 셋으로 예측한 비율 | trace 중앙값 1.065, 시간 가중 1.051 |

- trace 하나에 명령 반복이 1~3회라 trace별 잡음이 크다. CPU 비율, wakeup 수와 비율의 상관은 각각 −0.09, −0.31로 약하다.
- 그래서 원인을 trace별로 가르지는 못한다. 다만 합으로는 clock과 CPU 대기만으로 측정값 근처가 나온다.
- 남는 1~2%p는 exit 증가(vCPU 시간의 약 0.2%)나 cache 쪽일 수 있다. 반복 차이 수준이다.

## 5. 독립 노드 3개를 겹친 균형

같은 조건의 독립 실행 3개를 노드 3개로 본 값이다. 원값은 [balance.json](balance.json)에 있다.

- excess: 2초 칸마다 노드 평균을 넘는 부하의 몫이다(순간 이동으로 옮길 수 있는 상한). 30초 평균으로 같은 값을 구한 것도 함께 적었다.
- 순위 상관: 노드 쌍의 시간 순위 상관이다.

| 조건 | CPU 평균 코어 | CPU excess 2초 / 30초 | CPU 순위 상관 | 시스템 평균 ms/s | 시스템 excess 2초 / 30초 | 시스템 순위 상관 |
|---|---|---|---|---|---|---|
| ×0.25, 32 | 1.6 | 15.8% / 8.3% | 0.18 | 88 | 20.7% / 13.0% | 0.01 |
| ×0.25, 64 | 3.2 | 13.2% / 9.2% | 0.24 | 146 | 15.3% / 8.1% | 0.02 |
| ×0.25, 128 | 6.7 | 8.3% / 4.5% | 0.46 | 283 | 10.9% / 5.9% | 0.05 |
| ×0.25, 192 | 10.9 | 7.1% / 4.7% | 0.53 | 473 | 11.2% / 5.5% | 0.08 |
| ×1, 96 | 1.0 | 18.2% / 9.3% | 0.10 | 96 | 16.4% / 8.6% | 0.14 |
| ×1, 192 | 2.0 | 12.3% / 4.8% | 0.22 | 169 | 11.6% / 6.1% | 0.19 |

- **VM이 많을수록 노드가 고르다.** 노드당 VM이 많아지면 CPU와 시스템 부하 모두 불균형 몫이 준다.
- **CPU 상관은 burst가 겹쳐서 생긴 것이 아니다.** 30초 이동 평균을 뺀 상관은 −0.06~0.07이다. 192개에서 0.53까지 오르는 것은 실행 구조(ramp 뒤 닫힌 loop)가 만드는 느린 공통 추세다.
- **시스템 시간은 노드마다 따로 움직인다.** 다만 이 시스템 시간에는 잠든 채 기다리는 lock 대기가 들어 있어서, CPU 사용량이 아니다.
- **처음 분석의 상관 0.97~1.0은 잘못된 값이었다.** 처음에는 측정 창 끝 2초 칸에 실행 종료 때 모든 VM을 끄는 lock 대기(약 30초 분량)가 들어갔고, 이것 때문에 시스템 부하의 원값 상관이 0.97~1.0으로 나왔다. 창 밖 칸을 빼도록 `node_series`를 고쳤다.

## 6. LLC와 메모리 대역폭 (Docker, K=120)

[pool 이동 실측](../pool-mover-20261105/README.md)과 같은 두 pool 구성(CPU 2-16, 17-31)과 같은 48개 trace를 썼다. K=120으로 360개 trace를 돌렸다. 두 조건을 비교했다.
- 공유: L3를 두 pool이 함께 쓰고, resctrl monitor만 붙인다.
- 분리: pool마다 private way 6개를 준다(cbm `003f`, `0fc0`). I/O와 공유하는 way 13-14와 way 12는 기본 group에만 남긴다. socket 1(L3 domain 1)은 건드리지 않았다.

원값은 [llc-k120.json](llc-k120.json)에 있다.

| 지표 | 공유 | 분리 |
|---|---|---|
| CPU 가중 slowdown | 3.02 | 2.99 |
| pool 0 / pool 1 LLC MPKI | 2.99 / 2.72 | 2.93 / 3.00 |
| pool 0 / pool 1 IPC | 1.69 / 1.77 | 1.70 / 1.70 |
| socket 메모리 대역폭 | 40.5 GB/s | 40.9 GB/s |
| pool별 대역폭 p99 | 30.5 / 28.7 GB/s | 29.6 / 30.3 GB/s |

- 상대 pool이 바쁠 때 MPKI가 조금 오르는 현상은 L3를 나눠도 그대로였다. LLC를 나눠 써서 생긴 일이 아니다.
- 메모리 대역폭은 peak의 약 11%다.
- LLC와 메모리 대역폭은 이 부하에서 경합 원인이 아니다.

## 7. 한계

- **workload가 좁다.** Python RL image만 썼다. 빌드가 무거운 다언어 image는 디스크 공간 때문에 지워서 이번에 쓰지 못했다. I/O가 많은 task 쪽 다양성이 좁다.
- **harness가 VM과 물리 코어를 나눠 쓴다.** harness의 SMT sibling 64-67은 VM이 쓰는 물리 코어 0-3과 같은 코어다.
- **bpftrace도 비용을 더한다.** Firecracker의 모든 syscall, 스케줄 이벤트, 모든 task의 lock 경합을 추적한다. 모든 조건에 같은 계측을 붙였다.
- **VM 생성·종료 시간은 재지 않았다.** 동시 192개에서 이 경로의 lock 대기가 크게 늘었다. VM을 자주 만들고 지우는 RL에서는 이 시간이 처리량에 들어갈 수 있다.
- **같은 kernel의 2노드 실행도 같은 경향이었다.** 15코어 노드 2개가 kernel 하나를 함께 쓴 microVM 실행(노드당 24, 96개)에서도 블록 latency는 32배, 명령은 중앙값 1.10배였다. 여기서 두 노드의 시스템 부하 원값 상관 0.99는 host 전체 정지가 양쪽에 함께 잡힌 탓이었다. 그래서 독립 실행을 겹치는 방법으로 바꿨다.
