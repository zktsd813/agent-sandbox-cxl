# sandbox 메모리·CPU 실측 (2026-11-18~19)

bud05에서 Firecracker microVM으로 agent sandbox를 노드 하나 가득 채워 보고, 메모리와 CPU 중 무엇이 먼저 막히는지 쟀다. 측정은 11-18 20:14부터 11-19 02:08(KST)까지 했다. 실행 전 계획은 아래 [0절](#0-무엇을-확인하나)부터 그대로 남겼다. 요약 수치는 [summary/](summary/)에, 원시 기록은 `experiments/footprint/.local/queue/20261118T2014/`(git 밖)에 있다.

## 결론

1. **세 종류 모두 메모리가 CPU보다 훨씬 먼저 막혔다.** 메모리가 다 찼을 때 CPU 사용률은 RL 9~10%, code interpreter 11~17%, SWE 20~40%였다. 조건: 노드 메모리 114 GiB, sandbox마다 vCPU 1개, 60코어(코어당 1.9 GiB)와 38코어(코어당 3.0 GiB).
2. **이 비율이면 CPU가 먼저 막히려면 코어당 DRAM이 훨씬 커야 한다.** 메모리 천장에서 CPU가 72%가 되는 코어당 DRAM은 SWE 5~6 GiB, code interpreter 10~11 GiB, RL 14~24 GiB다.
3. **값싼 줄이기가 크다. CPU가 남으니 그 비용도 낼 수 있다.**
   - 30초 넘게 안 쓴 page: RL 81%, SWE 45%, code interpreter 29%.
   - lz4 압축 뒤 크기: 0.41~0.47.
   - 같은 내용 page를 노드 안에서 합치면 59~74%가 준다. 상한이고, 같은 task를 여러 sandbox가 돌린 것이 부풀렸다.
   - 압축만 해도 RL은 메모리가 절반 가까이 준다. 압축과 중복 제거를 모두 하면 SWE는 코어당 약 2 GiB에서 CPU가 먼저 막히는 쪽으로 넘어간다.
4. **snapshot·pause는 대기가 긴 종류에서 크게 듣는다.** 계산값이다.
   - RL은 10초 넘는 대기만 내려도 메모리의 84%가 빈다. 대가로 내렸던 sandbox의 다음 명령이 중앙값 46 ms, p90 131 ms 늦어진다.
   - code interpreter는 5초 넘는 대기에서 88%가 빈다. 셀이 0.1 ms라 배수로는 매우 크다.
   - SWE는 대기가 짧아(중앙값 1.7초) 10초 기준으로 22%만 빈다.
5. **넘치면 swap 비용은 종류와 넘친 비율에 따라 크게 갈렸다(SATA SSD).** sandbox 수를 고정하고, 끝난 자리를 바로 채우며, 메모리 예산만 줄였다(결과 4c, 11-19 오후).
   - RL: 1.5배에서 CPU 가중 명령 배수 1.03으로 거의 그대로다. 2배에서 1.19이고 명령 11%가 2배 넘게 늦었다(p90 2.2배). 3배에서 2.07이다.
   - SWE: 1.13배에서 이미 1.56이다. 1.34배 2.1, 1.7배 4.6(명령 중앙값 3배, SSD 99%), 2.4배 8.7, 3.3배 10.4다. 60초 timeout과 OOM이 났다. 무거운 test·build가 직전에 쓴 page를 다시 읽어서다.
   - swap에서 1 MiB를 다시 읽을 때마다 명령이 RL 24~30 ms, SWE 100~200 ms 늘었다. 늘어난 시간은 Python import·pytest 같은 소수 명령에 몰렸다.
   - page 기록 계산(결과 4b)은 SWE의 다시 읽는 양을 맞혔고, RL은 2~4배 적게 봤다.
   - 오전의 넘치기(결과 4: 1.30배에서 swap이 차오르는 8분만 1.09배, 뒤로는 그대로)는 sandbox가 한꺼번에 뜨고 더 들어오지 않은 쉬운 경우였다.
   - 처음 RL 재측정은 다른 세션의 VM 실행이 같은 SSD를 써서 부풀었다(2배에서 1.51). 측정 잠금을 잡고 다시 쟀다.
   - 압축(zswap)은 압축한 page도 DRAM에 남아 RL에서도 ×2를 넘지 못한다(계산).
   - 실험 1의 천장 근처에서는 공유 image의 page cache가 먼저 밀려났다. CI는 VM 부팅 p99가 294 ms에서 612 ms로 늘었다.
6. **SWE는 이 서버에서 디스크가 메모리보다 먼저 막혔다.** sandbox 160~240개에서 SATA SSD 쓰기가 포화했다(사용률 89~97%, 쓰기 160 MB/s). 명령이 2.5배(p99 30배) 늦어졌다. testbed 성질이 크다.
7. **천장 수는 간단한 계산과 10% 안에서 맞았다. CPU 사용률은 종류에 따라 크게 틀렸다.**
   - 메모리 천장은 "(예산 − 12 GiB) ÷ sandbox당 메모리"로 −8~+6% 안에서 맞았다.
   - 38코어 CPU 사용률은 60코어 기록으로 예측했다. code interpreter는 +8%였고, SWE는 −20%, RL은 +60% 틀렸다. RL은 trajectory 단계에 따라 sandbox당 CPU가 0.012~0.021로 흔들렸다.
   - 시간 시계열 simulator 확장은 마감 안에 하지 못했다.
8. **메모리를 늘리는 방법별 1차 계산(결과 7, 상한).** CXL 코어당 2 GiB는 ×2.2다. 압축 + 합치기는 RL ×4.6, SWE ×3.2, CI ×4.5다. snapshot은 RL ×6.2, CI ×6.1, SWE ×1.3이다. 지연 비용은 빠진 값이다.

**이야기에 주는 뜻(판단).**
- 전제 "메모리가 막는다"는 vCPU 1개 sandbox에서 세 종류 모두 강하게 섰다.
- 그러나 메모리를 늘리는 방법의 경쟁이 세다. CPU가 60~90% 남아서 압축(zswap)과 중복 제거(KSM)의 CPU 비용이 거의 공짜다. RL·code interpreter처럼 대기가 긴 종류는 snapshot도 메모리를 크게 비운다.
- CXL 용량이 이기려면 두 가지 중 하나를 보여야 한다. 압축·중복 제거·snapshot을 다 한 뒤에도 메모리가 남는다는 것, 또는 그 방법들이 내는 명령 지연(복원 수십 ms, swap 꼬리)을 CXL은 내지 않는다는 것이다.
- swap 실측은 두 번째 쪽을 일부 받친다. SATA swap은 RL 1.5배까지만 싸고, SWE에는 1.1배부터 쓸 수 없다. 다만 NVMe swap과 zswap은 재지 않았다. 둘 다 1 MiB당 비용이 훨씬 작을 것이라, CXL과 나란히 재야 판정할 수 있다.
- hand-off가 할 일은 이 비율에서 거의 없다. CPU가 10~40%라서다. 줄이기를 다 한 뒤 SWE 같은 종류에서 CPU가 차기 시작할 때 생긴다.

## 결과 1. 메모리 천장과 그때의 CPU

메모리가 막힌 단계의 값이다. 자리 받기가 그 단계 시간의 절반 넘게 막혔고 남은 자리가 20 GiB 아래였다. 1-rl만 예외로 마지막 단계 값이며, 메모리가 막히지 않았다. 명령 배수는 같은 trace·같은 순번의 명령을 첫 단계(또는 경합이 없던 1-rl, 1-swe, 1-ci 전체)와 비교한 값이다. network를 쓰는 명령은 뺐다.

| 종류 | 실행 | 코어 | 예산 | 살아 있는 sandbox | sandbox당 메모리 | sandbox당 CPU(논리) | CPU 사용률 | 명령 배수(CPU 가중) | CPU가 먼저 막히는 코어당 DRAM |
|---|---|---|---|---|---|---|---|---|---|
| RL | 1-rl(천장 전) | 60 | 139 GiB | 397 | 0.195 GiB | 0.012 | 3.8% | 0.98 | 24 GiB |
| RL | 1-rl-hi | 60 | 114 GiB | 547 | 0.201 GiB | 0.021 | 9.4% | 1.12 | 14 GiB |
| RL | 3-rl-38 | 38 | 114 GiB | 572 | 0.193 GiB | 0.013 | 9.7% | 1.03 | 22 GiB |
| SWE | 1-swe-hi | 60 | 113 GiB | 221 | 0.444 GiB | 0.107 | 19.7% | 2.49(디스크) | 6.0 GiB |
| SWE | 3-swe-38 | 38 | 114 GiB | 229 | 0.436 GiB | 0.132 | 39.7% | 1.65(디스크) | 4.8 GiB |
| CI | 1-ci | 60 | 114 GiB | 1,047 | 0.092 GiB | 0.013 | 11.1% | 1.05 | 10.3 GiB |
| CI | 3-ci-38 | 38 | 114 GiB | 1,055 | 0.092 GiB | 0.012 | 16.5% | 1.00 | 11.1 GiB |

- **마지막 열(교차점).** 2 × 0.72 × sandbox당 메모리 ÷ sandbox당 논리 CPU다. SMT를 켜서 물리 코어 하나가 논리 CPU 둘이다. 0.72는 11-16·11-18 simulator에서 CPU 천장이 오는 사용률이다. 이 값보다 코어당 DRAM이 적으면 메모리가 먼저 막힌다.
- **RL은 오래 살수록 커진다.** sandbox당 0.15 → 0.23 GiB였다(trajectory 중앙값 28분). 받은 뒤 자라는 몫 때문에 1-rl-hi에서 cgroup OOM이 났다. 3-rl-38에서도 마지막 단계에 살아 있는 수가 572개에서 441개로 줄었다. 그래서 메모리 천장은 측정 시간에 따라 달라진다. 오래 머물수록 낮다.
- **SWE의 명령 지연은 디스크 때문이다.** SWE 160개(1-swe-hi)에서는 1.12배였다. 240 단계의 2.5배·1.65배는 sda 사용률 97%, I/O 압력 20~40% 때문이다. 메모리 압력은 0.13% 이하였다.
- **CI는 30분 동안 sandbox 26,446개가 떴다 졌다.** CPU 사용률의 상당 부분이 VM을 띄우는 비용이다.

## 결과 2. 메모리 안: 식은 것, 압축, 같은 내용

표본 sandbox(동시에 32개)의 값이다. 압축과 중복 제거는 실제로 켜지 않고 page 내용으로 계산한 상한이다.

| 종류 | 30초 넘게 안 쓴 page | 120초 넘게 | lz4 압축 뒤(식은 page) | 0 page | 같은 내용을 합칠 때 감소 | 그중 같은 group 형제 | group 밖 | 압축만 했을 때 남는 비율 | 압축 + 합치기 뒤 남는 비율 |
|---|---|---|---|---|---|---|---|---|---|
| RL | 81% | 63% | 0.41 | 7% | 59% | 43% | 9% | 0.52 | 0.22 |
| SWE | 45% | 5% | 0.47 | 4% | 59% | — | 49% | 0.76 | 0.31 |
| CI | 29% | 1.5% | 0.42 | 12% | 74% | — | 65% | 0.83 | 0.22 |

- **"같은 내용" 감소는 상한이다.** SWE는 trace 12개를 sandbox 수백 개가 나눠 돌았다. 같은 task의 복제가 많아서 group 밖 49%가 부풀었다. CI는 300 trajectory가 모두 같은 image(Python, numpy, sympy)를 쓴다. 실제 fleet에서 다른 task 사이에 남는 몫은 RL의 group 밖 값(9%)에 가까울 것으로 본다(추정).
- **RL의 group 형제 사이 43%는 실제 GRPO 조건이다.** 같은 task의 rollout 8개가 같은 image와 같은 설치를 한다.
- **압축은 CPU를 쓴다.** 메모리가 찼을 때 CPU가 60~90% 남으므로 그 CPU를 쓸 수 있다. 압축·해제 지연은 재지 않았다.
- **교차점을 줄이기 뒤로 옮기면** 교차점 × 남는 비율이다.
  - 압축만 하면: RL 7~13, SWE 3.7~4.6, CI 8.6~9.2 GiB/core.
  - 압축 + 합치기를 다 하면: RL 3~5, SWE 1.5~1.9, CI 2.3~2.4 GiB/core.

## 결과 3. snapshot·pause 계산

**어떤 snapshot을 가정했나.** 계산이 암묵적으로 정한 조건이다. node 규모에서 중요한 변수는 바꿔 보지 않았다.

| 변수 | 계산의 가정 | 근거 | 바꿔 보지 않은 것 |
|---|---|---|---|
| 무엇을 뜨나 | sandbox마다 자기 snapshot. 처음 한 번 전체(VM 1.25초 멈춤), 그다음 바뀐 page만 | 11-18 실측은 sandbox별 전체 snapshot | image마다 공유하는 base snapshot. 공유하면 base page는 page cache에 한 벌만 두고, sandbox별 차이만 저장소에서 읽는다 |
| 어디에 두나 | 로컬 NVMe(990 PRO)의 복원 비용 | 11-18 실측은 NVMe | 이 testbed의 VM 디스크는 SATA SSD다. 원격 저장소도 없다 |
| page cache | snapshot 파일이 page cache에 없다(메모리를 실제로 비운 경우) | 11-18 실측은 있음·없음 두 조건을 나눠 쟀다. 계산은 "없음"을 썼다 | 파일이 page cache에 남으면 메모리가 비지 않는다. 실제 host에서는 일부만 남는 섞인 상태가 된다 |
| 복원 방식 | Firecracker 기본 lazy 복원(파일을 mmap, 처음 건드릴 때 읽음) | 11-18 실측 | 미리 읽기(working set 기록 후 prefetch) |
| 동시성 | 한 번에 VM 하나 | 11-18 실측 | 수백 개가 같은 저장소에서 동시에 내리고 올리는 경합 |
| 다시 읽는 양 | memscan이 5초 단위로 센, 다음 명령이 건드린 page | 이번 기록 | 5초 안의 guest 배경 접근이 섞여 과대일 수 있다 |

**swap과 같은 곡선 위에 있다.** sandbox 전체를 대기 시작에 내리는 snapshot은 "대기 동안 안 쓴 page를 모두 밀어내는 swap"과 같다. RL에서 10초 넘는 대기를 내리면 84%가 빈다. 다시 읽기는 p90 약 51 MiB다. 결과 4b에서 10초 넘게 안 쓴 page를 밀어내는 swap은 88%가 비고 p90 45 MiB를 다시 읽는다. 둘의 차이는 1 MiB를 다시 읽는 비용(파일 순차 읽기 대 swap 4 KB 무작위 읽기)과, VM 프로세스까지 내리는지에 있다.

표본 sandbox의 대기마다 다음을 셌다.
- 대기 직전에 있던 page 수
- 그중 다음 명령이 다시 건드린 page(disk 복원이면 다시 읽어야 한다)
- 앞 대기 이후 바뀐 page(diff snapshot 크기)

비용은 11-18 bud05 복원 실측으로 정했다: 복원 호출 18 ms + 다시 읽는 1 MiB당 2.2 ms. "비는 메모리"는 대기 동안(snapshot 뜨는 1.25초 제외) 내려가 있는 메모리 × 시간을, 대기와 명령 전체의 메모리 × 시간으로 나눈 값이다.

| 종류 | 대기 중앙값 | 내리는 대기 | 내린 대기 비율 | 비는 메모리 | 내린 명령의 지연 p50 / p90 | 명령 전체 평균 지연 | diff snapshot 쓰기(sandbox당) |
|---|---|---|---|---|---|---|---|
| RL | 13.1초 | 10초 넘는 것 | 56% | 84% | 46 / 131 ms | 40 ms | 0.40 MiB/s |
| RL | | 30초 넘는 것 | 22% | 54% | 53 / 131 ms | 16 ms | 0.15 MiB/s |
| SWE | 1.7초 | 전부 | 100% | 58% | 64 / 298 ms | 136 ms | 8.2 MiB/s |
| SWE | | 10초 넘는 것 | 5% | 22% | 58 / 111 ms | 4 ms | 0.73 MiB/s |
| CI | 8.8초 | 5초 넘는 것 | 100% | 88% | 45 / 56 ms | 47 ms | 0.26 MiB/s |
| CI | | 10초 넘는 것 | 31% | 43% | 45 / 59 ms | 15 ms | 0.08 MiB/s |

- **RL과 CI는 메모리를 크게 비운다.** 대기가 sandbox 시간의 대부분이라서다. 내린 명령마다 수십 ms가 붙는다. RL 명령은 대개 수십 ms라 2~3배이고, CI 셀은 0.1 ms라 수백 배다.
- **SWE는 대기가 짧아 비울 것이 적다.** 전부 내리면 sandbox당 diff snapshot 쓰기가 8 MiB/s다. 220개면 1.8 GB/s라, 이 서버의 SATA SSD(160 MB/s에서 포화)로는 불가능하다.
- **다시 읽는 양 중앙값(약 12 MiB)에는 바닥이 섞여 있다.** memscan은 5초 단위로 센다. 그래서 명령이 아닌 guest 배경 접근도 들어간다. 가벼운 명령의 실제 지연은 이보다 작을 수 있다. 11-18 실측에서 cache에 없을 때 가벼운 첫 명령은 +26~36 ms였다.
- **빠진 것.** 수백 개가 동시에 복원할 때의 disk 경합, snapshot을 뜨는 동안 VM이 멈추는 비용(diff snapshot), 복원 뒤 page cache 재적재는 넣지 않았다.

## 결과 4. 넘치기(thrashing): RL

RL sandbox 392개를 목표로 고정하고 자리 받기 없이 22분 돌렸다. 메모리 예산은 1-rl이 쓴 양(77 GiB, file cache 포함)의 100%, 80%, 65%다. swap은 이 cgroup에만 16 GiB(sda3, SATA SSD 파티션 전체)를 허락했다. 살아 있는 수는 4분쯤 390개로 가장 많고, GRPO group이 끝나며 300개까지 줄었다. 메모리 수요(anon + swap + kernel)는 13.5분에 가장 컸다. 값은 `experiments/footprint/overflow_detail.py`의 출력([summary/overflow-detail.txt](summary/overflow-detail.txt))이다.

| 예산 | 실제 overcommit(최대 수요 ÷ 예산) | swap 최대 | 메모리 압력(full, 2분 평균의 최대) | OOM |
|---|---|---|---|---|
| 77 GiB | 0.87배(넘치지 않음) | 0 | 0% | 0 |
| 62 GiB | 1.08배 | 5.1 GiB | 2.6% | 0 |
| 50 GiB | 1.30배 | 15.1 GiB | 4.4% | 3(10분, 13분) |

명령 시간은 같은 trace·같은 순번 명령의 1-rl 중앙값과 비교했다. network 명령은 뺐다.

- **비용은 밀어낼 때 난다.** 1.30배에서 swap이 0.9 GiB에서 15 GiB로 차오르는 4–12분에 늦어짐이 몰렸다. 가장 늦어진 명령은 pytest, cfn-lint 같은 무거운 test로 +1.4~3.0초(×1.2~4.4)였다. 상위 1% 명령이 늘어난 시간의 36%를 냈다.
- **12–22분이 그대로인 것은 수요가 줄어서다.** 처음 4분에 group 49개(392개)가 뜬 뒤 18분 동안 7개만 들어왔다. 메모리 수요는 13.5분에 가장 컸고 그 뒤로 sandbox가 끝나며 줄었다. 밀어낼 새 메모리가 없었다. sandbox가 계속 들어오는 RL이라면 밀어내는 구간이 계속된다(추정).
- **밀려난 것은 다시 쓰이지 않는 메모리였다.** swap에 12~15 GiB가 남아 있어도 다시 읽기는 초당 170~450 page(약 1~2 MB/s)였다. 표본 sandbox에서 명령 시작 때 60 MiB 넘게 swap에 나가 있던 명령 259개도 CPU 가중 1.04였다. 1.30배는 10분 넘게 안 쓴 page만 밀어내는 수준이라서다(결과 4b).
- **4–12분의 늦어짐은 다시 읽기보다 밀어내기에서 왔다.** 그 구간의 swap 다시 읽기는 초당 400~900 page(2~4 MB/s)로 작았다. 메모리를 비우는 회수와 SSD 쓰기가 원인으로 보인다(추정).
- **자주 쓰는 page가 메모리를 넘는 진짜 thrashing은 없었다.** RL에서 자주 쓰는 page는 sandbox당 약 40 MiB(0.2 GiB의 19%)라 330개면 약 13 GiB다. 예산 50 GiB보다 훨씬 작다. 그 전에 swap 장치(16 GiB)가 차서 OOM이 먼저 왔다.
- **1.08배의 12–22분 p99 2.14는 noise 범위다.** 무거운 명령 191개 중 2~3개가 만든 값이다. 10분 뒤 전체로 본 p99의 95% 구간이 1.13~2.75로, 넘치지 않은 실행(1.13~1.50)과 겹친다.
- **처음 정리(11-19 02시)를 고쳤다.** 앞 10분을 빼고 세어 swap이 차오르는 구간이 빠졌고, 1.30배의 비용이 1.01로 보였다. "1.25배·1.5배"라는 이름도 file cache까지 넣은 사용량 기준이었다. 실제 넘친 비율은 1.08배·1.30배다.
- **실험 1에서도 RL OOM이 났다.** 자리 받기에 남겨 둔 12 GiB(sandbox당 약 22 MB)로는 RL이 받은 뒤 자라는 몫을 못 받았다.

**실험 1에서 본 page cache 밀려남.** 자리 받기는 file cache를 비울 수 있는 것으로 셌다. 그래서 천장 근처에서 공유 image의 page cache가 먼저 밀려났다.

## 결과 4b. swap·압축 비용 곡선(page 기록으로 계산)

넘치기 실험은 swap에 쉬운 경우만 봤다. 더 넘치면 어떻게 되는지 표본 sandbox의 page 접근 기록(5초마다 쓰였는지)으로 계산했다. `experiments/footprint/miss_curve.py`, [summary/miss-curve.json](summary/miss-curve.json).

- **모델.** A초 넘게 안 쓴 page를 모두 밀어낸다(나이 기준 LRU). 그동안 비는 메모리와, 밀려난 page를 다시 쓰는 양(swap에서 읽는 양)을 센다.
- **swap 용량 배수** = 1 ÷ (1 − 비는 비율).
- **압축(zswap) 용량 배수** = 1 ÷ (1 − 비는 비율 × (1 − lz4 압축률)). 압축한 page는 DRAM에 남는다. lz4 압축률은 RL 0.41, SWE 0.47, CI 0.42다.
- **노드 swap 읽기** = 메모리 천장 수 × swap 배수 × sandbox당 읽기다.
- **ms 환산**은 11-18 snapshot 복원 실측(NVMe, VM 하나, 1 MiB당 2.2 ms)을 참고로만 붙였다. SATA SSD의 4 KB 무작위 읽기와 zswap 해제 비용은 재지 않았다.

| 종류 | A(안 쓴 시간) | 비는 비율 | swap 배수 | 압축 배수 | 명령당 다시 읽기 p90 / p99 | 10 MiB 넘게 읽는 명령 | 노드 swap 읽기 | p99 ms 환산 |
|---|---|---|---|---|---|---|---|---|
| RL | 600초 | 0.33 | ×1.5 | ×1.24 | 0.1 / 3.7 MiB | 0.6% | 8 MiB/s | 8 ms |
| RL | 300초 | 0.49 | ×2.0 | ×1.40 | 0.2 / 11 MiB | 1.2% | 25 MiB/s | 25 ms |
| RL | 120초 | 0.64 | ×2.8 | ×1.61 | 1.4 / 40 MiB | 3.8% | 160 MiB/s | 90 ms |
| RL | 30초 | 0.80 | ×5.1 | ×1.90 | 22 / 98 MiB | 16% | 1.1 GiB/s | 215 ms |
| RL | 10초 | 0.88 | ×8.4 | ×2.08 | 45 / 120 MiB | 27% | 3.0 GiB/s | 265 ms |
| SWE | 60초 | 0.22 | ×1.3 | ×1.13 | 0.4 / 28 MiB | 1.9% | 170 MiB/s | 60 ms |
| SWE | 30초 | 0.41 | ×1.7 | ×1.28 | 2.8 / 208 MiB | 6.1% | 840 MiB/s | 460 ms |
| SWE | 20초 | 0.53 | ×2.2 | ×1.39 | 7.2 / 291 MiB | 8.8% | 1.5 GiB/s | 640 ms |
| SWE | 10초 | 0.69 | ×3.2 | ×1.57 | 17 / 400 MiB | 13% | 3.1 GiB/s | 880 ms |
| CI | 30초 | 0.30 | ×1.4 | ×1.21 | 0.2 / 13 MiB | 1.2% | 72 MiB/s | 28 ms |
| CI | 20초 | 0.46 | ×1.8 | ×1.36 | 1.2 / 13 MiB | 2.7% | 190 MiB/s | 29 ms |
| CI | 10초 | 0.65 | ×2.8 | ×1.60 | 7.5 / 17 MiB | 5.8% | 790 MiB/s | 37 ms |

RL은 1-rl(표본 61개, 21.7 sandbox-시간), SWE는 1-swe-hi(335개, 12시간), CI는 1-ci(1,037개, 14.5시간)다. 38코어 실행도 같은 곡선이었다.

- **넘치기 실험은 표의 첫 줄 근처였다.** RL 1.30배는 10분 넘게 안 쓴 page만 밀어내는 수준이다. 계산한 swap 읽기(8 MiB/s 안팎)도 실측(밀어낸 뒤 1~2 MB/s, 밀어내는 동안 2~4 MB/s)과 같은 자릿수다.
- **RL은 swap으로 ×2 근처까지 싸다.** 5분 넘게 안 쓴 page만 내보내도 메모리가 반이 빈다. 그보다 더 넘치면 노드 swap 읽기가 SATA SSD로 받기 어려운 수준이 된다.
- **SWE는 ×1.7에서 이미 thrashing에 가깝다.** 무거운 명령(p99)이 직전 test·build에서 쓴 page를 수백 MiB 다시 읽는다. 다시 읽기의 98~99%가 명령 안에서 난다. 노드 전체로는 초당 840 MiB를 읽어야 해서, 이 SATA SSD로는 불가능하다.
- **CI는 sandbox가 짧게 살아서 식은 메모리 자체가 적다.**
- **압축은 압축률이 상한을 정한다.** 10초 넘게 안 쓴 page를 다 압축해도 RL ×2.1, SWE ×1.6, CI ×1.6이다. 그때 다시 읽기(해제)는 swap 같은 줄과 같다. 결과 7의 "압축 RL ×1.9"는 30초 기준이고, 명령의 16%가 10 MiB 넘게 해제하는 지점이다.
- **빠진 것.** 밀어내는 비용(회수, SSD 쓰기)은 넣지 않았다. 넘치기 실험의 4–12분 늦어짐은 주로 이쪽에서 왔다. 기록 간격이 5초라 A가 10~20초인 줄은 한 간격만큼 불확실하다.
- **실측(결과 4c)과 비교하면** 다시 읽는 양은 SWE에서 이 계산과 비슷했고, RL에서 2~4배 많았다. 1 MiB당 비용은 위 ms 환산(2.2 ms)보다 11~90배 컸다(SATA SSD의 4 KB 무작위 읽기).

  - 2배: 명령 중앙값은 그대로(1.02)다. 그러나 11%가 2배 넘게 늦었고, 늘어난 시간의 81%를 상위 10% 명령이 냈다. 무거운 명령은 p99 2.9배, 최대 7배였다.

  - 가장 늦어진 10% 명령은 거의 모두 Python 스크립트(2배 45개, 3배 62개)와 pytest(43개, 25개)였다. 예: `import tensorflow`가 1.7초에서 12초(2배), 1.95초에서 23.7초(3배). LLM 대기 동안 밀려난 guest page cache(library)와 heap을 다시 읽는 것으로 보인다(추정).

  - SWE는 100~200 ms/MiB다. 자기 swap 쓰기로 SSD가 60~99% 찼다.
  - 결과 4b의 ms 환산 기준(NVMe에서 snapshot 파일을 순차로 읽는 값, 2.2 ms/MiB)의 11~90배다.
- **kernel은 계산보다 더 많이 다시 읽었다(RL).** 실제 overcommit에 맞는 결과 4b 줄과 비교하면, swap 읽기가 RL 1.5배에서 약 2배(계산 약 0.9 MiB/s, 실측 1.8), 2배에서 약 4.4배(계산 약 2 MiB/s, 실측 9.3), 3배에서 약 2.8배(약 14 대 39 MiB/s)였다. SWE 1.7배는 진행 속도로 보정하면 계산과 비슷했다(약 90 대 100 MiB/s). 계산은 page마다 안 쓴 시간을 아는 이상적인 순서다. kernel 회수는 LLM 대기로 오래 쉬는 RL page의 나이를 그만큼 가려내지 못하는 것으로 보인다(추정, kernel 설정은 바꿔 보지 않았다).
- **결과 4의 "swap은 싸다"는 RL 1.5배까지만 맞다.** 살아 있는 수가 유지되면 RL도 2배에서 꼬리가 늘고, SWE는 1.13배부터 늦어진다.
- **한계.** SATA SSD 한 개이고 VM 쓰기 디스크와 함께 쓴다. NVMe swap이면 1 MiB당 비용이 작아질 것이다(재지 않았다). 노드 하나, 조건마다 한 번이다. 실행 시간(SWE 12분, RL 25분) 동안 RL sandbox가 계속 자라 실제 비율이 실행 끝으로 갈수록 올랐다. vCPU 1개다.

- **sandbox마다 vCPU가 1개다.** vCPU를 2~4개 주면 무거운 명령이 짧고 굵어진다. 평균 CPU는 비슷하겠지만, 몰리는 정도와 SWE 명령 시간이 달라진다.

## 0. 무엇을 확인하나

11-18 simulator는 sandbox 메모리를 Docker 재생의 cgroup 값에서 가져왔다. 거기에는 명령마다 process가 끝나 guest kernel, guest page cache, 계속 떠 있는 process가 없다. 그래서 메모리가 병목인지 정할 수 없었다([image-capacity-20261118](../image-capacity-20261118/README.md)). 이 측정은 microVM에서 다음 다섯 질문에 답한다. 실험은 세 개뿐이고(4절), 질문 2·3은 실험 1의 기록으로 계산한다.

| 질문 | 답하는 방법 | 이야기에서의 자리 |
|---|---|---|
| **1. 메모리가 정말 먼저 막히나** | 노드를 실제로 채운다. sandbox는 메모리에 자리가 있을 때만 받는다. 메모리 때문에 더 못 받는 수(메모리 천장)와 명령이 SLO를 넘는 수(CPU 천장) 중 어느 쪽이 먼저 오는지 본다. 메모리가 찼을 때 노는 CPU도 잰다. 코어당 2.5 GiB(60코어)에서 직접 보고(실험 1), 4 GiB(38코어)는 실험 3으로 확인한다. 2 GiB는 계산한다 | 전제. 아니면 1단계(CXL 용량)가 설 자리가 없다 |
| **2. 값싼 줄이기 뒤에도 남나** | sandbox마다 메모리를 자주 쓰는 것, 식은 것, 다른 sandbox와 겹치는 것, 압축되는 정도로 나눈다. 압축(zswap), 중복 제거(KSM), image 공유를 계산으로 빼고 1을 다시 본다 | 압축·중복 제거는 연구 범위 안이다(11-18). 이것만으로 풀리면 CXL이 필요 없다 |
| **3. snapshot·pause가 얼마나 비우고 얼마를 내나** | LLM 대기마다 sandbox를 내린다고 할 때, 비는 메모리와 다음 명령이 다시 읽는 양(지연), snapshot 쓰기 양(대역폭)을 sandbox 기록으로 계산한다 | 이겨야 할 대안이다. 아래에 따로 적었다 |
| **4. 넘치면 무슨 일이 나나** | 메모리 천장을 일부러 넘긴다. page를 다시 읽는 양(refault), swap, 메모리 압력(PSI), 명령 시간, OOM을 본다 | 천장은 "평균 상주"가 아니라 "평균 상주 + 몰릴 때의 여유"다. 그 여유를 thrashing이 정한다. 넘치는 몫을 CXL이 받는 쓰임의 근거도 된다 |
| **5. simulator가 실측과 맞나** | 1의 기록만 넣은 simulator가 실측 천장(sandbox 수, 그때 CPU 사용률)과 10% 안에서 맞는지 본다 | 맞으면 코어당 8 GiB, 큰 노드, 정책 조합을 simulator로 넓힌다 |

**판정**(6절): 대부분이 코어당 4 GiB에서도 메모리 쪽이고 2·3을 빼도 차이가 남으면 메모리 이야기가 선다. 계속 떠 있는 process가 있는 종류만 메모리 쪽이면 그 종류를 중심으로 세운다. 대부분이 코어당 2.5 GiB에서도 CPU 쪽이면 전제가 약하다.

### snapshot: agent에서는 효과가 serverless보다 작을 것이다

사용자 판단(11-18): snapshot은 agent에서도 듣지만 serverless나 VM에서만큼 크지 않을 것이다. 같은 날 다른 세션의 측정(옛 checkout `docs/results/restore-first-cmd-20261118/`, git 밖)이 그 이유를 수치로 보인다.

| | serverless 함수, 쉬는 VM | agent sandbox |
|---|---|---|
| 쉬는 구간 | 호출 사이 수 분~수 시간 | LLM 대기. RL iter2 중앙값 7.7초, Gemini SWE는 절반이 2초 미만 |
| 복원 횟수 | 호출마다 한 번 | 명령마다. RL trajectory 하나에 명령 중앙값 89개 |
| 복원 비용이 어디에 붙나 | 호출 하나에 한 번 | 매 turn의 다음 명령. disk에서 복원하면 무거운 명령 +0.2~1.5초, 가벼운 명령 3~8배(쓰던 page 1 MiB당 약 2.2 ms) |
| page cache에 두고 복원 | — | 빠르지만(첫 명령 +7 ms) 메모리를 아끼지 못한다. 파일 2 GiB에 고쳐 쓴 page가 따로 더 생긴다 |
| snapshot 뜨기 | 드물다 | full snapshot 1.25초, 2 GiB 쓰기. 대기마다 뜨면 2초 미만 대기에서는 다음 명령이 기다린다 |

그래서 agent에서 snapshot이 비울 수 있는 메모리는 "긴 대기 동안의 식은 메모리"로 줄어든다. 이 부분은 압축과 CXL도 노리는 곳이다. 3번 질문은 이것을 sandbox 기록으로 잰다.
- 대기 길이별로 내릴 수 있는 시간
- 다음 명령이 다시 읽는 page 양: 대기 직전에 있던 page 중 다음 명령이 쓴 것
- 대기마다 바뀐 page 양: diff snapshot 크기. 노드 전체로 더하면 필요한 disk 쓰기 대역폭이 된다

이 셋으로 "대기가 T초보다 길 때만 내린다" 정책의 메모리 절감과 명령 지연을 T별로 낸다. 비교 대상은 같은 식은 메모리를 압축하거나 CXL에 두는 경우다.

## 3. 재는 것: simulator 입력이 되도록

sandbox마다 아래 시계열을 남긴다. 측정 process는 측정용 코어(0-3, 64-67)에서만 돈다.

| 묶음 | 내용 | 주기 | 방법 | 대상 |
|---|---|---|---|---|
| 사건 | 명령(셀) 시작과 끝, return code. 그 사이가 LLM 대기 | 사건마다 | guest agent가 serial에 찍는 표시 | 전부 |
| CPU | vCPU thread의 실행과 runqueue 대기, VMM thread의 실행 | 100 ms, VMM은 1초 | `/proc/<tid>/schedstat` | 전부 |
| host가 쥔 메모리 | VMM의 RssAnon(= guest가 쓰고 아직 돌려주지 않은 RAM), RssFile | 1초 | `/proc/<pid>/status`. free page reporting으로 돌려준 page는 빠진다 | 전부 |
| guest 안 구성 | MemFree, Cached, AnonPages, Shmem, Dirty, disk 읽기·쓰기 | 2초 | guest agent가 `/proc/meminfo`를 serial로(기존 기능) | 전부 |
| 식은 메모리 | guest RAM page마다 마지막으로 쓰인 시각. 30초·120초 넘게 안 쓰인 양 | 5초 | host idle page tracking(KVM EPT A bit, bud05 `ept_ad=Y`) | 표본 |
| 바뀐 page | 직전 5초에 쓰기가 있었던 page | 5초 | soft-dirty(pagemap bit 55, `clear_refs 4`) | 표본 |
| page 목록 | 5초마다 접근한 page와 쓴 page의 bitset | 5초 | 위 둘. 대기 뒤 다음 명령이 다시 쓰는 page를 뒤에서 계산한다 | 표본 |
| 내용 | page마다 64-bit hash, 0 page 여부. 일부 page의 압축률(lz4, zlib) | 5분, 그리고 VM마다 처음 한 번 | `/proc/<pid>/mem`에서 있는 page만 읽는다 | 표본 |
| 노드 | cgroup 메모리(anon, file, kernel), 남은 자리, PSI, OOM, CPU 사용률, refault(file, anon)·major fault·회수한 page(thrashing 징후) | 1초 | cgroup, `/proc/stat` | — |

- **표본**은 동시에 32개다. 끝난 표본 자리는 새 sandbox가 채운다. 목표가 48개 이하인 첫 단계에서는 모두 잰다.
- **soft-dirty의 부담.** 지울 때마다 guest가 page에 처음 쓸 때 EPT fault가 한 번 더 난다. 표본 sandbox만 이 부담을 지므로, 표본과 나머지의 명령 시간을 따로 보고한다.
- **image page cache**는 따로 재지 않는다. page hash를 측정 뒤 base image의 4 KiB block hash와 맞춰서 센다. guest kernel page도 같은 방법으로 센다.

이 기록으로 sandbox마다 시간에 따라 다음을 낸다.
- **전체**: host가 쥔 메모리
- **자주 쓰는 것**: 30초 안에 쓴 page
- **식은 것**: 나머지. 압축·CXL·snapshot으로 옮길 수 있는 후보
- **겹치는 것**: 다른 sandbox와 같은 내용인 page. 0 page, guest kernel, image, 같은 task 형제로 나눈다
- **압축률**: 식은 page를 압축했을 때 남는 비율
- **대기마다**: 대기 길이, 대기 전에 있던 page 중 다음 명령이 다시 쓴 양(snapshot 복원 때 읽을 양), 대기 사이에 바뀐 양(diff snapshot 크기)

## 4. 실험 세 개

사용자 결정(11-18 20:40): 실험 종류는 핵심만, 세 개 이내.

| 실험 | 무엇을 | 답하는 질문 | 시간 |
|---|---|---|---|
| **1. 채우기** | RL(GRPO group 8), 다언어 SWE, CI를 60코어·메모리 전부(약 150 GB, 코어당 약 2.5 GiB)에서 하나씩. 목표 수를 5~7분마다 올리고 메모리에 자리가 있을 때만 받는다 | 1(직접), 2·3(기록으로 계산), 5(입력) | 1.7시간 |
| **2. 넘치기** | RL을 실험 1에서 닿은 수로 고정하고, 메모리 예산을 실험 1이 쓴 양의 100%, 80%, 65%로 줄인다(overcommit 1.0, 1.25, 1.5). 자리 받기 없음. 이 cgroup에만 swap 16 GB(SATA SSD)를 허락한다 | 4 | 1.1시간 |
| **3. 코어당 4 GiB** | RL과 CI를 실험 1에서 닿은 수로 38코어에서 돌린다. 메모리는 그대로 | 5(직접 확인) | 0.7시간 |

**실험 1: 채우기**(`fill.py`)
- **자리 받기.** sandbox(RL은 group 8개)는 자리가 있을 때만 받는다. 자리 = 예산 − (cgroup 메모리 − file cache). 12 GiB를 비워 두고 받는 sandbox마다 0.5 GiB를 더 요구한다.
  - 메모리가 먼저 막히면 살아 있는 수가 목표 아래에서 멈춘다. 그 수가 메모리 천장이다.
  - CPU가 먼저 막히면 목표대로 늘고 명령 시간이 늘어난다. 각 단계의 명령 시간을 첫 단계(코어 사용률 50% 아래)와 비교해 SLO(CPU 가중 1.10배, 무거운 명령 p99 2.0배)를 넘는 수를 찾는다.
- 자리 받기는 file cache를 비울 수 있는 것으로 센다. 그래서 천장 근처에서는 image page cache가 밀려나 다시 읽기가 먼저 올 수 있다. refault와 메모리 압력이 오르면 "thrashing으로 막힌 천장"으로 따로 적는다.
- 표본 sandbox 32개(첫 단계는 전부)는 memscan이 식은 메모리, 바뀐 page, page 내용을 잰다(3절). 압축·중복 제거(질문 2)와 snapshot(질문 3)은 이 기록으로 계산한다.
- **SWE는 LLM 대기 ×1만 돌린다.** ×4는 simulator에서 대기만 늘려 계산한다. 대기 중 메모리가 거의 일정하다는 가정이고, 실험 1의 기록으로 그 가정을 확인한다.

**실험 2: 넘치기**(thrashing)
- RL을 고른 이유: 실제 RL 기록이고, GRPO group 형제가 같은 task라 무거운 명령이 같이 몰린다. thrashing이 가장 먼저 나올 경우다.
- 단계마다 22분. sandbox는 처음 4분에 걸쳐 띄우고, 메모리가 자라면서 넘친다.
- 보는 것
  - 넘치는 순서: page cache 다시 읽기 → swap → OOM 중 어디까지 가나
  - 명령 시간: 실험 1 첫 단계 대비 배수
  - 메모리 압력(PSI)
  - 끝나지 못한 sandbox
- 100%에서도 file cache가 밀리므로 page cache thrashing만 보일 것이다. 80%와 65%는 sandbox 메모리 자체가 swap으로 나간다.
- zswap은 host 전체 설정이라 쓰지 않는다. 압축으로 넘친 몫을 받는 경우는 질문 2의 압축률로 계산한다.

**실험 3: 코어당 4 GiB**
- 메모리가 먼저 막히는 종류라면 sandbox 수는 같고, CPU 사용률만 60/38배로 오른다. 이때 명령이 SLO를 넘는지가 simulator 예측과 맞는지 본다.
- 실험 1에서 메모리 쪽으로 나온 종류만 의미가 있다. SWE는 CPU 쪽일 것이라 뺐다.

**계산으로 하는 것**(실행 없음)
- 압축(zswap), 중복 제거(KSM), image 공유: 실험 1 표본의 식은 page, 압축률, page hash로 뺀다.
- snapshot·pause: 대기가 T초보다 길 때 내린다고 보고, 비는 메모리와 다음 명령 지연(다시 읽는 양 × 1 MiB당 2.2 ms), disk 쓰기 양을 T별로 낸다.
- simulator 보정: 실험 1의 첫 단계 기록만 넣어 실험 1의 다른 단계와 실험 3을 맞춰 본다. 천장에서의 sandbox 수와 그때 CPU 사용률이 10% 안이어야 한다. 맞으면 코어당 8 GiB, 큰 노드(128·192코어)로 넓힌다.

## 5. simulator에 더할 것

[`capsim.py`](../../../experiments/capsim/capsim.py)는 지금 sandbox 메모리를 한 덩어리로 본다. A의 기록을 넣으려면 다음을 더한다.

- **입력**: sandbox마다 10 ms CPU, 1초 메모리(자주 쓰는 것, 식은 것, image page, 겹치는 page 종류별), 압축률, 단계와 대기 사건
- **자리 받기**: 실제 상주로 받고, 몰릴 때를 위한 여유를 둔다(여유 비율은 실험 2의 thrashing 시작점으로 정한다)
- **정책**

  | 정책 | 계산 |
  |---|---|
  | 압축(zswap) | 식은 page × 압축률. 압축·해제 CPU를 더한다 |
  | 중복 제거(KSM) | 노드 안의 겹치는 page를 한 벌로 |
  | image 공유 배치 | image page를 노드 안 한 벌로, 묶음 크기 b |
  | CXL | 식은 page(또는 명령 사이 상태)를 CXL에, 단계 종류별 tax |
  | snapshot·pause | 대기가 T초보다 길 때 내린다. 내려간 동안 메모리가 빈다. 다음 명령은 대기 전 page 중 다시 쓰는 양 × 1 MiB당 2.2 ms(disk 복원, 11-18 측정)를 기다린다. 뜨기는 바뀐 page 양만큼 disk에 쓴다. T를 sweep한다 |

- **sweep**: 코어당 DRAM 2·2.5·4·8 GiB, 노드 코어 60·128·192, workload 섞기

이 확장은 측정이 도는 동안 쓰고, 끝나면 돌린다. 11-18 결과의 메모리 쪽을 이것으로 바꾼다. 마감 안에 다섯 정책을 모두 한다.

## 6. 판정

workload마다 다음을 낸다.
- 메모리 ÷ CPU = (sandbox당 시간 평균 메모리 + 공유분 몫) ÷ sandbox당 평균 CPU
- 기준 = 노드 메모리 ÷ (B에서 잰, SLO를 지키는 최대 CPU 사용량)
- 메모리 천장에서의 CPU 사용률(놀고 있는 CPU)
- 코어당 4·8 GiB로 옮긴 결과(모양 2 실측과 simulator)
- 압축·중복 제거·image 공유를 한 뒤에도 남는 차이

| 결과 | 뜻 |
|---|---|
| 순서 1 종류 대부분이 코어당 4 GiB에서도 메모리 쪽이고, 압축 뒤에도 차이가 남음 | 메모리 이야기가 선다. 1단계(CXL 용량)를 세운다 |
| 계속 떠 있는 process가 있는 종류(HARN, CI, DESK, WEB)만 메모리 쪽 | 그 종류를 중심으로 이야기를 세운다. 코딩 agent는 CPU 쪽으로 둔다 |
| 대부분이 코어당 2.5 GiB에서도 CPU 쪽 | 메모리가 병목이라는 전제가 약하다. 이야기를 다시 정한다 |

hand-off가 필요한지는 이와 따로, CXL을 붙인 뒤 CPU가 차는 종류가 있는지로 판단한다.

  - `drop_caches`, KSM 끄기·켜기(지금 `run=1`), zswap은 그때 승인을 받는다.
- **받을 것**
  - 작은 것: Terminal-Bench 2.0 trajectory, ReTool·PyMath 코드 셀
  - 중간: OpenHands runtime image
  - 큰 것: OSWorld VM image와 trajectory, AgentLab trace 일부, WebArena 사이트 image
  - 다른 세션이 디스크 지연을 재고 있을 수 있으므로, 큰 다운로드는 그 실험이 끝난 뒤에 한다.

  - 기존 microVM image가 137 GB다. 새 image를 만들기 전에 지울 것을 사용자와 정한다. VM마다 쓰기 디스크는 sparse이고 끝나면 지운다.
- **비용**: DA의 API LLM(순서 3)은 모델과 예산을 정해야 한다.
- **쓰지 않는 것**: node 2(DCD)는 쓰지도, 늘리거나 줄이지도 않는다. dockerd는 다시 시작하지 않는다.

**줄인 방법**
1. **실험은 세 개다**(4절). 단독 실행은 채우기의 첫 단계로 합쳤다.
2. **목표 한 단계는 10분이다.** 마지막 단계만 15~30분 머문다.
3. **종류는 RL, SWE ×1, CI다.** SWE ×4와 코어당 2 GiB는 실행하지 않고 계산한다. image는 모두 있다(CI image는 11-18에 빌드).
5. **마감 뒤로 미룬 것**
   - TERM, HARN: task image 변환과 runtime image 받기가 필요하다. 받기는 다른 세션의 cold 재생(디스크 읽기)과 겹치면 안 된다.
   - 순서 2·3(DESK, WEB, DA)
   - 압축 실행(E): 압축률은 page 표본으로 재고, zswap을 켜는 실측만 미룬다.
