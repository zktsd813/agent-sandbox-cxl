# 노드 사이 불균형과 배치 방식 (2026-11-18)

simulator 분석이다. 실측을 새로 하지 않았다. 질문은 두 가지다.

1. 메모리를 노드에 고르게 나누면 CPU나 다른 자원에는 불균형이 없나?
2. image 위치를 빼면, 덜 바쁜 노드에 배치하는 방식(노드 k개를 뽑아 가장 덜 바쁜 곳)을 쓰지 않을 이유가 있나? 그 배치로 불균형이 풀리나?

입력과 모델은 [11-16 용량 simulator](../capacity-cxl-20261116/README.md)와 같다. 코드는 [`experiments/capsim/`](../../../experiments/capsim/)에 있다. `capsim.py`에 불균형 집계와 배치 선택 옵션(`place_k`, `place_metric`)을 더했고, 기본값은 11-16 실행과 같은 결과를 낸다. 실행은 bud04 NUMA 0에서 했다(`balance.py` 24회, `place.py` 126회).

## 0. 결론

1. **메모리는 노드에 고르게 나뉘지만 CPU는 그렇지 않다.** CXL을 붙이고 이동이 없을 때, 노드 사이 CV(표준편차 ÷ 평균)는 메모리 예약 0.07~0.15, CPU 수요 0.29~0.60이다. 1초 평균으로 봐도 CPU CV가 0.28~0.57이라 순간적인 흔들림이 아니다. 가장 바쁜 노드의 CPU는 평균의 1.6~2.4배다.
2. **넘친 CPU는 대부분 다른 노드가 놀 때 생긴다.** 노드 코어를 넘친 수요는 전체 수요의 14~16%다. 그중 다른 노드의 빈 코어로 받을 수 있던 몫이 8.4~15.2%다. hand-off를 켜면 넘친 수요가 4.7~6.4%로 준다.
3. **배치 방식을 바꿔도 이 불균형은 남는다.** 7가지 배치 중 가장 좋은 것도 CPU 가중 명령 시간이 1.100~1.117배이고, CPU CV는 0.28~0.59다. 2개를 뽑아 CPU가 낮은 쪽을 고르는 기존 방식과의 차이는 0.015 이내로, seed 사이 차이(약 0.01)와 비슷하다. 배치할 때는 앞으로 올 burst를 모르기 때문이다([11-05 실측](../pool-mover-20261105/README.md): 넓게 쓰는 sandbox의 40%는 수명의 1/4이 지난 뒤에야 처음 넓게 쓴다).
4. **hand-off는 배치 방식과 관계없이 1.03배 근처다**(1.028~1.038). 무거운 명령 p99는 가장 좋은 배치의 1.63~1.70에서 1.15~1.21로 준다.
5. **전체 노드에서 지금 CPU가 가장 낮은 곳을 고르면 오히려 나쁘다**(1.124~1.155). 새 sandbox는 LLM 대기부터 시작해서 처음에는 CPU를 쓰지 않는다. 그래서 방금 여러 개를 받은 노드가 계속 한가해 보이고, 새 sandbox가 그 노드에 몰린다. 2개만 뽑거나, sandbox 수나 예약 메모리를 기준으로 하면 이 문제가 없다.
6. **메모리가 막히면 고를 노드가 없다.** DRAM만 쓰면 코어당 0.27~0.56개가 자리를 기다리고, 메모리 예약 CV는 0.01 이하다. 7가지 배치가 모두 같은 결과를 낸다. CPU를 보고 고르는 배치는 메모리에 여유가 있을 때만 뜻이 있다.
7. **이 조건에서는 노드 사이 용량 공유의 이득이 없다.** 메모리가 이미 고르게 나뉘므로, 노드별 CXL과 공유 pool은 이동이 없을 때 결과가 같다.
8. **CPU 밖 자원은 모델에 없다.** CPU와 메모리 용량만 다룬다. 여러 노드가 pool 장치 하나를 쓸 때의 대역폭, 디스크, network는 보지 않았다. 실측에서는 microVM 192개까지 이벤트당 비용이 평평했고([11-06](../microvm-system-20261106/README.md)), LLC 점유가 단계 뒤 1초 안에 빠졌다.

**요약.** 덜 바쁜 노드에 두는 배치는 써야 할 기본값이다. 피할 이유는 image·형제 sandbox 위치와, 노드를 비워 두려는 packing 정도다. 다만 배치로는 CPU 불균형이 풀리지 않는다. 비교는 "가장 좋은 배치"와 "같은 배치 + hand-off"로 한다.

## 1. 설정

| 항목 | 값 |
|---|---|
| cluster | 16노드, 노드당 48/96/192코어, DRAM 2 GiB/코어. CXL은 없음, 노드별 8 GiB/코어(expander), 16노드가 공유하는 pool(코어당 8 GiB와 같은 총량) |
| 밀도 | pool 8 GiB/코어, 이동 없음에서 SLO 한계 근처. sandbox 자리/코어 = 48코어 0.85, 96코어 1.05, 192코어 1.2 |
| 상주 메모리 | `hwm`(guest는 한 번 쓴 메모리를 돌려주지 않음) |
| 시간 | 준비 600초 + 측정 2,400초, seed 1·2 |
| 배치 | 메모리 예약이 맞는 노드 중에서 고른다. `place_k`개를 뽑아 key가 가장 작은 곳, 맞는 곳이 없으면 맞는 노드 전체에서 key가 가장 작은 곳. key는 직전 step의 CPU 수요, sandbox 수, 예약 메모리 중 하나 |

지표(측정 구간의 10 ms step마다 계산해 평균):
- **CV**: 노드 사이 표준편차 ÷ 노드 평균. 메모리는 예약(guest 크기 합)과 상주(명령 사이 상태 + 실행 중 새 메모리)를 따로 본다.
- **최대/평균**: 가장 큰 노드 ÷ 노드 평균.
- **넘친 수요**: Σ max(0, 노드 수요 − 코어) ÷ Σ 수요.
- **다른 노드가 받을 수 있던 몫**: min(넘친 양의 합, 다른 노드 빈 코어의 합) ÷ Σ 수요.
- 1초 값은 노드별 수요를 100 step 평균한 뒤 같은 식으로 계산했다.

## 2. 메모리와 CPU의 불균형 (`balance.jsonl`)

CXL을 붙이고 이동이 없는 경우다. 노드별 CXL과 공유 pool의 결과가 같아서 한 줄로 적는다.

| 지표 | 48코어 | 96코어 | 192코어 |
|---|---|---|---|
| CPU 사용률 | 0.66 | 0.80 | 0.90 |
| 메모리 예약 CV | 0.15 | 0.10 | 0.07 |
| 메모리 예약 최대/평균 | 1.29 | 1.20 | 1.14 |
| 상주 메모리 CV | 0.24 | 0.15 | 0.09 |
| CPU 수요 CV (10 ms) | 0.60 | 0.41 | 0.29 |
| CPU 수요 CV (1초) | 0.57 | 0.40 | 0.28 |
| CPU 최대/평균 (1초) | 2.37 | 1.91 | 1.61 |
| 넘친 수요 | 15.5% | 13.9% | 14.2% |
| 그중 다른 노드가 받을 수 있던 몫 | 15.2% | 12.5% | 8.4% |
| CPU 가중 명령 시간 | 1.115 | 1.108 | 1.117 |

같은 밀도에서 hand-off를 켜면(공유 pool, 10 ms):

| 지표 | 48코어 | 96코어 | 192코어 |
|---|---|---|---|
| CPU 수요 CV (10 ms) | 0.43 | 0.25 | 0.15 |
| 넘친 수요 | 6.4% | 4.7% | 5.0% |
| CPU 가중 명령 시간 | 1.036 | 1.029 | 1.035 |
| 무거운 명령 p99 | 1.20 | 1.16 | 1.16 |
| 이동/초 (cluster 전체) | 3.4 | 10.4 | 36.0 |

DRAM만 쓰는 경우(메모리가 막힘)는 다음과 같다.
- 메모리 예약 CV는 0.010/0.004/0.002로, 모든 노드가 꽉 차 있다.
- CPU CV는 0.66/0.45/0.31이다.
- CPU 사용률이 0.40이라, 실제로 넘친 수요는 2.8/0.3/0.0%로 작다.
- 코어당 0.27/0.44/0.56개가 자리를 기다린다.

같은 부하에서 명령 시간이 1.115에서 1.036으로 약 7% 준다. [11-05 Docker 실측](../pool-mover-20261105/README.md)의 −6%(K=120, CPU 가중)와 비슷하다. 11-16의 처리량 +10~33%는 이 차이를 "같은 SLO에서 부하를 얼마나 더 받나"로 바꾼 값이다.

## 3. 배치 방식 (`place.jsonl`)

CPU 가중 명령 시간(seed 2개 평균)이다. 공유 pool, 이동 없음.

| 배치 | 48코어 | 96코어 | 192코어 |
|---|---|---|---|
| 무작위 1개 | 1.142 | 1.141 | 1.184 |
| 2개 뽑아 CPU가 낮은 쪽 (기존) | 1.115 | 1.108 | 1.117 |
| 4개 뽑아 CPU가 낮은 쪽 | 1.112 | 1.112 | 1.119 |
| 전체에서 지금 CPU가 가장 낮은 노드 | 1.127 | 1.124 | 1.155 |
| 2개 뽑아 sandbox 수가 적은 쪽 | 1.109 | 1.111 | 1.125 |
| 전체에서 sandbox 수가 가장 적은 노드 | 1.107 | 1.109 | 1.131 |
| 전체에서 예약 메모리가 가장 적은 노드 | 1.100 | 1.105 | 1.122 |
| hand-off (위 7가지 배치) | 1.035~1.038 | 1.028~1.031 | 1.032~1.035 |

- 무거운 명령 p99는 가장 좋은 배치가 1.70/1.68/1.63, hand-off가 1.20~1.21/1.15~1.16/1.15~1.16이다.
- CPU CV는 배치에 따라 0.585~0.648 / 0.396~0.464 / 0.283~0.376이다. 무작위가 가장 크고, 나머지는 0.6/0.4/0.3 근처에 모인다.
- seed 사이 차이는 같은 배치에서 0.001~0.025다. 2개 뽑기, 4개 뽑기, sandbox 수, 예약 메모리 기준 사이의 차이는 이 범위 안이다.
- DRAM만 쓰는 경우 7가지 배치의 명령 시간은 모두 1.013~1.017 / 1.001~1.002 / 1.000이다.

## 4. 한계

- 다언어 build·test 264 trace만 썼다. GRPO group(같은 task의 rollout이 함께 시작)은 없다. trace를 무작위로 넣는다. 11-05 실측에서는 group이 한 노드에 몰리면 기다린 시간의 85%가 거기서 생겼다. 형제 sandbox를 서로 다른 노드에 두는 규칙이 따로 필요하다.
- 자리 받기는 guest 크기 전체를 예약한다(상주는 그 약 40%). memory overcommit을 전제로 하면 자리를 받은 뒤 메모리가 늘어 노드마다 달라질 수 있다. 그때 노드 사이 용량 공유가 뜻을 가질 수 있지만 여기서는 보지 않았다.
- 노드를 비워 끄거나 큰 sandbox 자리를 남기려고 몰아 넣는 packing은 넣지 않았다.

cd experiments/capsim
