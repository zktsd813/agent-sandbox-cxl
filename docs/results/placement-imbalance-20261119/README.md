# 배치 기준과 노드 불균형: memory overcommit에서 (2026-11-19)

simulator 분석이다. 입력은 11-18 footprint 실측(Firecracker microVM, vCPU 1개)의 sandbox별 1초 단위 메모리·CPU다. 노드끼리 옮기는 일은 없다.

**질문(사용자, 11-19).** CPU를 보고 least-k로 나누면 메모리가 고르지 않게 되고, 메모리를 보고 나누면 CPU가 고르지 않게 되지 않을까?

[11-18 배치 분석](../capacity-balance-20261118/README.md)은 자리를 받을 때 guest 크기 전체를 예약했다. 그래서 받은 뒤 자라는 메모리가 만드는 불균형은 보지 못했다. 여기서는 아무것도 예약하지 않는다. 노드는 sandbox를 받고, 그 메모리는 실측 시계열대로 자란다(overcommit).

## 결론

1. **CPU를 보고 고르면 메모리가 고르지 않게 된다. 맞다.**
   - SWE, CPU당 DRAM 2 GiB, 평균 메모리 95% 조건에서 비교했다.
   - 2개 뽑아 지금 CPU가 낮은 쪽을 고르면, 노드가 DRAM을 넘는 시간이 25%다. 예상 메모리로 고르면 7.7%다.
   - 전체에서 CPU가 가장 낮은 노드를 고르면 36%이고, 노드 메모리 p99가 DRAM의 1.55배다.
2. **메모리를 보고 고를 때 CPU가 고르지 않게 되는지는 메모리를 무엇으로 재느냐에 달렸다.**
   - **지금 쓰는 메모리로 고르면 SWE에서 메모리와 CPU가 둘 다 나빠진다.**
     - 2개 뽑기: DRAM을 넘는 시간 29%, CPU CV 0.21이다. 무작위는 19%, 0.12다.
     - SWE 메모리는 명령 중에 튀었다 빠진다. 그래서 지금 값이 앞으로를 잘 말해 주지 않는다.
     - 새 sandbox는 부팅 직후 메모리만 보인다. 그래서 막 받은 노드가 계속 가장 비어 보인다.
   - **예상 메모리(살아 있는 sandbox 수 × 종류별 평균)로 고르면 메모리와 CPU가 둘 다 가장 고르다.** SWE에서 CPU CV가 0.12로, CPU를 보고 고른 경우(0.19)보다 낮다.
3. **갈림길은 "CPU냐 메모리냐"가 아니라 "지금 값이냐 예상 부하냐"다.**
   - 한 종류 안에서는 sandbox당 메모리와 CPU가 모두 sandbox 수에 비례한다. 그래서 수를 고르게 하면 둘 다 고르다.
   - 지금 값은 CPU든 메모리든 몇 초 단위로 흔들린다. 거기에 맞춰 고르면 잠깐 조용한 노드로 몰린다.
   - 둘을 함께 보는 규칙은 예상 메모리 하나보다 나았던 적이 없다.
     - "예상 메모리로 거른 뒤 CPU로 고르기"는 SWE 2 GiB에서 DRAM 초과 16%, CPU CV 0.16이다.
     - "예상 메모리 비율 + 최근 CPU 비율 합"은 그 사이다.
     - 섞기 기준으로 다시 CPU 지금 값을 넣기 때문이다.
4. **가장 좋은 규칙으로도 남는 불균형은 메모리 쪽이다.**
   - SWE는 평균 95%에서 노드가 DRAM을 넘는 시간이 7.7%(CPU당 2 GiB), 2.1%(4 GiB)다.
   - 노드별 여유로 막으려면 p99 기준 DRAM의 3.6%와 0.6%가 노드마다 더 필요하다.
   - 같은 넘침을 노드들이 함께 쓰는 pool로 받으면 p99 기준 클러스터 DRAM의 1.0%와 0.2%면 된다. 노드마다 따로 남기는 것의 1/3 안팎이다.
   - RL은 메모리가 천천히 고르게 자라서, 좋은 규칙이면 넘치지 않는다.
   - 그러나 크기 자체가 작다. 노드 여유 몇 %를 공유 pool로 바꾸는 이득이다.
5. **vCPU 1개 sandbox에서는 CPU 불균형의 비용이 작다.**
   - 평균 CPU가 98%인 SWE(4 GiB)에서도 예상 메모리 규칙은 공정 분배 늘어짐이 1.03이다.
   - CPU를 보고 고르면 1.08, 전체에서 가장 낮은 노드는 1.35다.
   - CPU 사용률이 32~65%인 RL과 섞은 경우에는 넘치는 일이 없다.
   - 11-18 sim의 CPU CV 0.3~0.6보다 작다. 그때는 Docker에서 코어 제한이 없는 다언어 SWE를 썼다.
   - 큰 sandbox가 CPU도 많이 쓰게 늘리면 달라진다. CPU당 DRAM 4 GiB인 SWE에서는 가장 나은 규칙으로도 CPU 일의 3.5%가 넘친다(아래 "CPU도 크기에 맞춰 늘리면").

## 사용자 판단(11-19 저녁): 지금 보이는 값으로 배치한다

- **예상 메모리 규칙은 기준선으로 쓰지 않는다.** 종류별 평균을 미리 안다고 두는 예측이다. agent sandbox는 무엇을 언제 얼마나 쓸지 예측할 수 없다는 것이 가장 큰 특징이라, 이 가정은 맞지 않는다.
- **배치는 지금 보이는 값(쓰는 메모리, CPU)으로 한다.** 거기서 생기는 쏠림은 피할 수 없다고 인정한다. 그 쏠림을 CXL pooling(노드끼리 메모리를 나눠 받음)과 hand-off(CPU가 넘치는 노드에서 옮김)로 완화한다.

이 기준에서 남는 쏠림(평균 메모리 95%, 2개 뽑기):

| 종류, CPU당 DRAM | 규칙 | DRAM 초과 시간 | 노드마다 남길 여유(p99) | 공유 pool로 받을 크기(p99) | CPU 늘어짐 |
|---|---|---|---|---|---|
| SWE, 2 GiB | 지금 메모리 | 29% | 12.5% | 3.1% | 1.00 |
| SWE, 2 GiB | 지금 CPU | 25% | 11.4% | 2.8% | 1.00 |
| SWE, 4 GiB | 지금 메모리 | 30% | 11.1% | 2.4% | **1.09** |
| SWE, 4 GiB | 지금 CPU | 26% | 9.5% | 1.9% | 1.08 |
| 섞기, 2 GiB | 지금 메모리 | 7.5% | 3.8% | 0.6% | 1.00 |
| 섞기, 2 GiB | 지금 CPU | 12% | 5.6% | 1.1% | 1.00 |
| RL, 2 GiB | 지금 메모리 | 0% | 없음 | 0 | 1.00 |
| RL, 2 GiB | 지금 CPU | 2.4% | 0.8% | 0.3% | 1.00 |

- **메모리 쪽.** SWE에서 노드마다 DRAM의 11~13%를 여유로 남겨야 할 쏠림을, 공유 pool은 클러스터 DRAM의 2~3%로 받는다. RL은 메모리가 천천히 고르게 자라 지금 메모리로 골라도 넘치지 않는다.
- **CPU 쪽.** CPU가 거의 찬 SWE(CPU당 4 GiB)에서만 늘어짐 1.08~1.09가 남는다. vCPU 1개 sandbox라 나머지 조건에서는 CPU가 넘치지 않는다. 이 몫이 hand-off가 할 일이다.
- 평균 메모리 85%에서는 지금 보이는 값 규칙도 거의 넘치지 않는다(SWE 0.4~1.7%의 시간). 쏠림은 메모리를 꽉 채워 쓸 때의 문제다.

**남은 위험: sandbox 수 기준 배치.**
- 살아 있는 sandbox 수도 지금 보이는 값이고 예측이 아니다. 많은 스케줄러가 이것으로 고른다.
- 이 시뮬레이션에서 수 기준 2개 뽑기는 예상 메모리 규칙과 거의 같았다. SWE 2 GiB에서 DRAM 초과 7.7%, 노드 여유 3.6%, 공유 pool 1.0%다.
- 리뷰어가 수 기준을 기준선으로 들고 오면 pooling이 받을 쏠림이 1/3로 준다.
- 대응은 둘 중 하나다.
  - 수 기준이 덜 듣는 조건을 보인다. 한 종류 안에서 sandbox 크기가 크게 다른 경우다. 이번 입력은 SWE trace 12개, RL group 39개뿐이라 그 다양성이 작다.
  - 수 기준도 기준선에 넣고, 그때 남는 몫으로 주장한다.
- 아래 "크기가 제각각일 때"에서 첫째를 확인했다. 크기를 넓히면 수 기준의 이점이 거의 사라진다.

## 크기가 제각각일 때(11-19 저녁)

**왜.** microVM 입력의 SWE는 trace 12개라 크기가 비슷했다(평균 374 MiB). 같은 다언어 SWE 264개를 10-14에 Docker로 재생한 기록(trace별 cgroup 최대 메모리, file cache 포함)은 꼬리가 길다.
- 중앙값 0.63 GiB, p90 4.7 GiB, p99 11.7 GiB, 최대 18 GiB(babel).
- 크기 CV 1.41이고, 상위 10% trace가 최대 메모리 합의 43%를 차지한다.
- 일반 VM만큼 큰 sandbox(데스크톱, 큰 C++/Rust build)도 있을 것이다. 다만 재지 않았다. 여기서는 우리 SWE 기록의 꼬리만 넣었다.

**넓히는 법.** SWE sandbox마다 위 분포에서 최대 메모리를 하나 뽑는다. 시계열에서 부팅 수준(처음 10초의 최소)을 넘는 부분을 늘려 그 최대에 닿게 한다. 그래서 큰 sandbox도 배치될 때는 작게 보이고, 그 뒤에 자란다. 넓힌 뒤 SWE의 시간 평균 메모리는 1.0 GiB(CV 1.43), 최대 메모리 p99는 11.9 GiB다. CPU는 실측 그대로 두었다. RL은 그대로다. `experiments/footprint/imbalance_wide.py`, [summary/wide.jsonl](summary/wide.jsonl). 모형과 설정은 위와 같다(16노드, CPU 96개, 1시간 데운 뒤 1시간, seed 2개, seed 차이 최대 0.05).

**SWE, 평균 메모리 95%**(괄호는 크기를 넓히기 전)

| 규칙 | DRAM 초과 시간(2 / 4 GiB) | 노드마다 남길 여유 p99(2 / 4 GiB) | 공유 pool p99(2 / 4 GiB) |
|---|---|---|---|
| 무작위 | 34% / 28% (19% / 9.6%) | 28% / 18% | 7.6% / 4.3% |
| 지금 CPU 2개 뽑기 | 34% / 31% (25% / 26%) | 31% / 22% | 7.3% / 5.5% |
| 지금 메모리 2개 뽑기 | 36% / 36% (29% / 30%) | 29% / 23% | 7.2% / 5.8% |
| 수 2개 뽑기 | **31% / 27%** (7.7% / 2.1%) | **22% / 14%** (3.6% / 0.6%) | **5.9% / 4.0%** (1.0% / 0.2%) |
| 지금 CPU 전체 | 38% / 37% | 68% / 67% | 15% / 14% |
| 지금 메모리 전체 | 38% / 37% | 76% / 62% | 16% / 14% |

**RL과 SWE 섞기, 평균 메모리 95%**

| 규칙 | DRAM 초과 시간(2 / 4 GiB) | 노드 여유 p99 | 공유 pool p99 |
|---|---|---|---|
| 무작위 | 28% / 20% | 19% / 12% | 4.4% / 2.6% |
| 지금 메모리 2개 뽑기 | 25% / 23% | 15% / 11% | 3.7% / 2.4% |
| 수 2개 뽑기 | 27% / 20% | 18% / 11% | 4.4% / 2.4% |
| 종류별 예상 메모리 2개 뽑기(참고, 예측) | 25% / 17% | 15% / 8.7% | 3.9% / 2.0% |

- **크기가 제각각이면 수 기준의 이점이 거의 사라진다.** SWE에서 DRAM 초과 시간이 7.7%에서 31%로 늘어, 지금 메모리 기준(36%)과 거의 같아졌다. 섞으면 수 기준이 지금 메모리 기준보다 나을 것이 없다. 수는 노드에 sandbox가 몇 개인지만 맞출 뿐, 큰 것 몇 개가 한 노드에 몰리는 것은 못 본다.
- **예측 규칙도 거의 듣지 않는다.** 종류별 평균은 같은 종류 안의 크기 차이를 모른다. 섞기에서 지금 메모리 기준과 비슷하다.
- **지금 보이는 값으로는 어느 규칙도 쏠림을 막지 못한다.** 평균 85%에서도 SWE 노드가 DRAM을 넘는 시간이 2개 뽑기 규칙에서 8.5~14%(CPU당 2 GiB)다(크기를 넓히기 전에는 0~1.7%).
- **공유 pool이 할 일이 4배쯤 커진다.** SWE(CPU당 2 GiB, 95%)에서 노드마다 DRAM의 22~31%를 여유로 남겨야 할 쏠림을, 공유 pool은 클러스터 DRAM의 6~8%로 받는다. 크기를 넓히기 전에는 1~3%였다.
- **CPU는 이 입력에서 넘치지 않았다**(사용률 18~41%, 늘어짐 1.000~1.002). sandbox가 커져 노드당 수가 줄었고, CPU를 크기에 맞춰 늘리지 않았기 때문이다. CPU도 늘린 결과는 아래 "CPU도 크기에 맞춰 늘리면"에 있다.

**한계.** Docker 최대 메모리는 file cache를 포함하고, 최대값이라 평균보다 크다. 시계열 모양은 12개 SWE trace의 것을 늘려 썼다. 큰 sandbox가 실제로 언제 자라는지는 재지 않았다.

## CPU도 크기에 맞춰 늘리면(11-20)

**왜.** 위 넓힌 입력은 CPU를 실측 그대로 두어 CPU가 넘치지 않았다. Docker 기록에서는 큰 trace가 CPU도 많이 쓴다. 최대 메모리와 평균 코어 수의 순위 상관이 0.82(CPU 시간과는 0.88)다. 코어 수는 최대 메모리에 비례하지 않고 약 0.5제곱으로 는다(log-log 기울기 0.48). 평균 코어 수는 중앙값 1.7, p90 5.6, 최대 10이다.

**늘리는 법.**
- 메모리를 뽑을 때 같은 trace의 Docker 평균 코어 수도 함께 뽑는다. 메모리 값은 11-19 실행과 똑같다(확인했다). 그래서 CPU를 보지 않는 규칙의 메모리 지표도 위 표와 같다.
- SWE 시계열에서 활성 초(0.05코어 초과)의 평균이 "뽑은 코어 수 × 0.65"가 되게 늘린다.
  - 0.65는 "microVM 활성 초 평균 ÷ Docker 평균 코어 수"의 중앙값이다(0.39~0.68).
  - vCPU 1개에 묶이지 않은 가벼운 trace 6개(Docker 평균 1코어 이하)에서 쟀다.
  - 1초 단위로 재면 부분 활성 초가 섞여 Docker 값보다 낮게 나온다. 그 차이를 맞추는 값이다.
- 한 sandbox가 1초에 vCPU 16개보다 많이 원하면, 넘는 몫은 다음 초로 미룬다. 버려진 일은 없었다. 상한을 8개로 해도 결과가 거의 같았다(CPU 초과 시간 차이 0.5%p 이하, [summary/widecpu8.jsonl](summary/widecpu8.jsonl)).
- 늘린 뒤 SWE sandbox는 평균 0.26코어를 쓴다(이전 0.11).
  - 메모리 1 GiB당으로는 0.26코어로 이전(0.29)과 비슷하다.
  - 총량은 거의 그대로이고, CPU가 큰 sandbox에 몰렸을 뿐이다. 1초 최대는 중앙값 1.8, p90 7.2코어다.
- 규칙에 "지금 메모리 비율 + 최근 10초 CPU 비율"(2개 뽑기, 전체)을 더했다. 둘 다 지금 보이는 값이다.
- 새 지표는 셋이다.
  - **CPU 초과 시간**: 노드의 CPU 수요가 코어 수를 넘는 노드-시간의 비율.
  - **넘친 일**: 코어 수를 넘은 CPU 수요 ÷ 전체 CPU 수요.
  - **옮길 곳 있는 몫**: 넘친 일 중 같은 초에 다른 노드의 빈 코어로 받을 수 있는 비율. 이동 비용 없이 1초마다 CPU를 쪼개 옮긴다고 둔 상한이다.
- `experiments/footprint/imbalance_wide.py widen --cpu-cap 16`, [summary/widecpu16.jsonl](summary/widecpu16.jsonl), [보고서](summary/widecpu16-report.txt).

| 지금 메모리 2개 뽑기 | 34% | 6.8% | 99% | 9.3% | 50% | 11% | 77% |
| 메모리 + CPU 2개 뽑기 | 32% | 5.7% | 99% | 5.9% | 50% | 10% | 75% |
| 지금 CPU 전체 | 37% | 15% | 100% | 19% | 46% | 19% | 87% |
| 지금 메모리 전체 | 37% | 17% | 100% | 23% | 45% | 22% | 89% |

**RL과 SWE 섞기, CPU당 DRAM 4 GiB, 메모리 95%**: 2개 뽑기 규칙에서 CPU 초과 시간 1.1~2.9%, 넘친 일 0.11~0.35%다. 전체에서 고르는 규칙은 10%, 2.3~2.6%다.

- **CPU가 넘치는지는 CPU당 DRAM이 정한다.**
  - 메모리 1 GiB당 CPU가 0.26코어라, CPU당 DRAM 2 GiB에서는 메모리를 95% 채워도 CPU 평균이 33~51%다.
  - 이때 2개 뽑기 규칙이면 노드가 CPU를 넘는 시간이 0.5% 이하이고, 넘친 일은 0.06% 이하다.
  - 메모리가 먼저 막히고 hand-off가 할 일은 거의 없다.
- **CPU당 4 GiB면 SWE에서 CPU가 메모리와 함께 막힌다.**
  - 메모리 85%에서 CPU 평균이 91%다. 가장 나은 규칙(수, 무작위)으로도 노드가 CPU를 넘는 시간이 28%이고, CPU 일의 3.5~3.7%가 넘친다. 공정 분배 늘어짐은 1.04다.
  - 넘친 일의 99%는 같은 초에 다른 노드에 빈 코어가 있었다. 이것이 hand-off가 받을 수 있는 몫의 상한이다.
  - 메모리 95%면 클러스터 CPU 평균이 101%로 전체가 모자란다. 넘친 일 7.7~11% 가운데 66~77%만 옮길 곳이 있고, 나머지는 어떤 이동으로도 풀 수 없다.
- **RL과 섞으면 CPU 쏠림은 작다**(CPU 평균 59~66%, 넘친 일 0.35% 이하). RL sandbox는 CPU를 거의 쓰지 않는다.
- **처음 질문("CPU로 고르면 메모리가, 메모리로 고르면 CPU가")에 대한 답.**
  - 둘 다 맞다. SWE 4 GiB 85%에서 지금 메모리로 고르면 CPU가 더 넘치고(넘친 일 6.8%, 수 기준 3.5%), 지금 CPU로 고르면 메모리가 더 넘친다(DRAM 초과 7.1%, 수 기준 2.8%).
  - 둘을 더한 점수도 수나 무작위보다 낫지 않다. 지금 값은 CPU든 메모리든 몇 초 단위로 흔들리기 때문이다.
  - 전체에서 가장 낮은 노드를 고르면 그 노드로 몰려 CPU 넘친 일이 15~17%다.
  - 크기가 제각각인 이 입력에서는 수 기준도 쏠림을 막지 못한다. 다만 두 자원 모두에서 지금 값 규칙보다는 덜 나쁘다.
- **이야기에 주는 뜻(해석).** CXL로 메모리를 늘리면 CPU당 메모리가 커진다(예: DRAM 2 GiB + CXL 2 GiB). sandbox가 더 들어가면 CPU가 메모리와 함께 차기 시작하고, 그때 CPU 쏠림이 hand-off의 몫이 된다. 이 sim에서 그 몫은 클러스터 CPU 평균이 90% 근처일 때 CPU 일의 약 4%다. CXL tax와 이동 비용은 넣지 않았다.

**한계.**
- CPU 세기는 Docker 즉시 재생(LLM 대기 없음, 코어 제한 없음)의 평균 코어 수에서 왔다. 0.65 보정은 trace 6개에서 나왔고 흩어짐이 0.39~0.68이다.
- 넘친 CPU 수요는 그 초에 사라진다고 셈한다. 실제로는 sandbox가 늦어져 수명이 늘고 부하가 더 쌓인다. 그래서 넘친 일은 낮게 잡혔을 수 있다.
- 옮길 곳 있는 몫은 상한이다. hand-off는 sandbox를 통째로 옮기고 비용이 있다.
- 1초 단위라 1초보다 짧은 burst는 평평해진다. RL은 그대로다.

## 설정

| 항목 | 값 |
|---|---|
| 노드 | 16개, 노드마다 CPU 96개 |
| DRAM | CPU당 2 GiB(노드 192 GiB) 또는 4 GiB(384 GiB) |
| 부하 | 평균 메모리 사용이 클러스터 DRAM의 85% 또는 95%가 되도록 도착률을 정한다(Poisson) |
| 종류 | RL만, SWE만, 섞기(메모리 기준 반반) |
| 시간 | 1시간 데운 뒤 1시간을 잰다, 1초 단위 |
| 반복 | seed 2개. 같은 조건의 seed 차이는 DRAM 초과 시간에서 최대 0.06이다 |

- **RL**: 1-rl과 3-rl-38에서 8개가 모두 끝까지 돈 GRPO group 39개(sandbox 312개)다. 한 group의 8개가 2초 안에 함께 도착한다. 수명 중앙값 12.6분, 평균 메모리 142 MiB, 평균 CPU 0.013이다.
- **SWE**: 1-swe에서 끝까지 돈 sandbox 548개(trace 12개)다. 수명 중앙값 2.1분, 평균 메모리 374 MiB, 평균 CPU 0.097이다.
- **메모리**는 Firecracker 프로세스의 RssAnon이다. image page cache와 host 몫은 없다.
- **CPU**는 vCPU와 VMM thread의 실행 시간이다.
- 노드당 sandbox 수(평균 95%): SWE 약 500·1,000개, RL 약 1,300·2,600개(2·4 GiB).

배치 규칙. 모두 도착 순간의 노드 상태를 본다.

| 이름 | 고르는 법 |
|---|---|
| 무작위 | 노드 하나를 무작위로 |
| CPU 2개 뽑기 / CPU 전체 | 최근 10초 CPU가 낮은 노드 |
| 메모리 2개 뽑기 / 메모리 전체 | 지금 쓰는 메모리가 적은 노드 |
| 수 2개 뽑기 | 살아 있는 sandbox 수가 적은 노드 |
| 예상 메모리 2개 뽑기 / 전체 | 살아 있는 sandbox의 종류별 평균 메모리 합이 적은 노드 |
| 예상 메모리로 거른 뒤 CPU 2개 뽑기 | 예상 메모리가 DRAM의 90% 아래인 노드 중 CPU가 낮은 쪽 |
| 2차원 합 2개 뽑기 | 예상 메모리 비율 + 최근 CPU 비율이 낮은 쪽 |

## 결과: 평균 메모리 95%

- DRAM 초과: 노드가 DRAM을 넘은 시간의 비율. 넘친 만큼 swap에 가야 한다.
- 노드 p99: 노드 메모리 ÷ DRAM의 p99. 노드마다 남겨야 할 여유다.
- 공유 pool p99: 넘친 양을 모든 노드에서 더한 값의 p99를 클러스터 DRAM에 대한 비율로 쓴 값. 노드끼리 나눠 쓰는 pool이 받아야 할 크기다.
- CPU 늘어짐: CPU 가중 공정 분배 늘어짐(1초 단위).

**SWE**

- CPU 사용률은 32%와 65%다. 어느 규칙에서도 CPU가 노드를 넘는 일은 거의 없다(늘어짐 1.000, CPU 전체만 1.027).
- 섞으면 종류별 평균을 쓰는 예상 메모리가 단순 수보다 낫다. RL(142 MiB)과 SWE(374 MiB)의 크기가 달라서다.
- GRPO 형제를 서로 다른 노드에 두면("예상 메모리로 거른 뒤 CPU" 규칙에만 붙여 봤다) CPU CV가 0.19 → 0.16(2 GiB), 0.20 → 0.14(4 GiB)로 준다. 메모리는 그대로다.

**RL**
- 메모리가 천천히 고르게 자라서 지금 쓰는 메모리로 골라도 잘 된다. 메모리 2개 뽑기의 CV가 0.003이다.
- CPU를 보고 고르면 DRAM 초과가 2.4%(2개 뽑기), 11%(전체)다. 무작위는 5.2%다.
- CPU 사용률 15~31%라 CPU는 어느 규칙이든 넘치지 않는다.

평균 메모리 85%에서는 예상 메모리 규칙이 모든 조건에서 넘치지 않는다. CPU 전체와 메모리 전체 규칙은 85%에서도 SWE가 14~21% 시간 넘친다. 모든 조건의 표는 [summary/report.txt](summary/report.txt)에 있다.

## 한계

- **simulator다.** 넘친 메모리가 swap으로 가서 느려지는 되먹임이 없다. 느려진 sandbox가 더 오래 살아 메모리를 더 잡는 효과도 없다. 11-19 swap 실측에서 SWE는 이 되먹임으로 시간이 갈수록 더 느려졌다.
- **CPU는 1초 평균이다.** 100 ms 아래의 burst는 평평해진다. 11-18 sim에서는 1초와 10 ms의 CV가 비슷했다.
- **입력이 좁다.** RL은 끝까지 돈 group만 써서 긴 rollout이 빠졌다(수명 중앙값 12.6분, 전체는 18분). SWE는 trace 12개를 되풀이한 것이다. CI는 수명이 짧아 넣지 않았다.
- **예상 메모리 규칙은 종류별 평균을 안다고 둔다.** 예측이라 기준선에서 뺐다(위 사용자 판단).
- **노드 사이 이동이 없다.** hand-off나 pool이 넘침을 얼마나 받는지는 "공유 pool p99"로만 어림했다.
