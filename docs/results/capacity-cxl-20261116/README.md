# CXL 용량 확장: 노드별 expander와 공유 pool, 이동 유무 (2026-11-16)

simulator 분석이다. 실측을 새로 하지 않았다. 질문은 세 가지다.

1. 메모리가 sandbox 수를 막을 때, CXL로 용량만 늘리면 노드당 처리량이 얼마나 느는가?
2. 그 뒤에 CPU 경합이 막는다면, 무거운 명령이 시작할 때 다른 노드로 옮기는 것이 얼마나 더하는가?
3. 노드마다 붙인 CXL expander와 여러 노드가 같이 쓰는 CXL pool은 어떻게 다른가? 복사(100/25 Gb/s)와 hand-off는 어떻게 다른가?

코드는 [`experiments/capsim/`](../../../experiments/capsim/)에 있고, 실행은 bud04 NUMA 0에서 했다(합계 16,314회).

## 0. 결론

같은 SLO(명령 시간 CPU 가중 평균 ≤ 1.10배, 무거운 명령 p99 ≤ 2.0배)를 지키는 최대 CPU 사용률이다. CPU 일의 양이 곧 처리량이므로 이 값으로 비교한다. CXL은 코어당 8 GiB이고, 메모리는 guest 크기만큼 예약한다(아래 2절).

| 노드 코어 | DRAM GiB/코어 | DRAM만 | +CXL, 이동 없음 | +CXL expander, 100G 복사 | +CXL expander, 25G 복사 | +CXL pool, hand-off 10 ms |
|---|---|---|---|---|---|---|
| 48 | 2 | 0.41 (메모리) | 0.63 | 0.82 (p99 1.73) | 0.67 (p99 2.00) | **0.84** (p99 1.41) |
| 48 | 4 | 0.65 | 0.63 | 0.82 | 0.67 | **0.84** |
| 96 | 2 | 0.42 (메모리) | 0.79 | 0.92 (p99 1.83) | 0.78 (p99 2.00) | **0.93** (p99 1.37) |
| 96 | 4 | 0.78 (메모리) | 0.79 | 0.92 | 0.78 | **0.93** |
| 192 | 2 | 0.42 (메모리) | 0.88 | 0.96 (p99 1.89) | 0.85 (p99 2.00) | **0.97** (p99 1.31) |
| 192 | 4 | 0.79 (메모리) | 0.88 | 0.96 | 0.85 | **0.97** |

1. **메모리가 막는 동안은 CXL 용량만으로 처리량이 크게 는다.** DRAM이 코어당 2 GiB면 DRAM만으로는 사용률 41~42%에서 메모리가 찬다. CXL을 붙이면 63/79/88%(48/96/192코어)까지 오른다(×1.5~2.1).
2. **용량을 늘리면 다음에는 CPU 경합이 막는다.** 이동이 없으면 노드 크기와 관계없이 63/79/88%가 상한이다. DRAM이 코어당 4 GiB면 메모리와 CPU가 거의 같은 곳에서 막혀서, CXL 용량만으로는 이득이 거의 없다(0.97~1.11배).
3. **CXL로 용량이 남는 상태에서는 명령 시작 때 옮기기가 처리량을 더 올린다.** hand-off는 이동 없음보다 +33/+18/+10%(48/96/192코어)다. 11-13 결과(노드 26/16/7% 절감)와 같은 방향이다. 메모리가 막는 구성(DRAM만, 또는 CXL이 작은 경우)에서는 옮겨도 이득이 없다. 남는 CPU를 쓰려면 sandbox를 더 받을 메모리가 있어야 하기 때문이다.
4. **이동이 없으면 expander와 pool은 같다.** 모든 구성에서 차이가 0.01 안이다. 노드마다 메모리가 남고 모자라는 정도가 sandbox 수가 많아 고르게 퍼지기 때문이다. Pond식 pooling 이득은 이 workload에서 보이지 않는다.
5. **공유 pool의 이득은 복사 없이 옮긴다는 데서 나온다.**
   - 100 Gb/s 복사는 처리량으로는 hand-off와 거의 같다(차이 1~2%p). 하지만 무거운 명령 p99가 1.73~1.89로, hand-off의 1.31~1.41보다 나쁘다.
   - 25 Gb/s 복사는 p99 2.0에 걸려 이동 없음과 비슷하거나 못하다(0.67/0.78/0.85).
   - 복사 쪽에 유리한 가정이 들어 있다. NIC를 다른 traffic이나 다른 이동과 나누지 않고, 출발 노드 CPU도 쓰지 않는다고 했다. 192코어에서 이동은 노드당 초당 약 4번이고 한 번에 약 1.6 GiB를 보낸다. 100G 링크의 절반 이상을 쓰고, 한 번에 약 140 ms가 걸린다.
6. **CXL tax는 작다.** 이전 상태를 CXL에 두고 무거운 명령이 새로 잡는 메모리를 DRAM에 두면, DRAM이 코어당 1 GiB뿐이어도 tax로 늘어난 CPU는 0.5~1.2%다.

**요약: 사용자 frame과 맞다.** CXL 용량이 1차 이득이다. 용량이 늘면 CPU가 막히고, 거기서부터 공유 CXL 위의 이동이 +10~33%를 더한다. 공유가 노드별 expander보다 나은 곳은 이동 비용이다. 100G 복사와 비교하면 tail, 25G와 비교하면 처리량 자체에서 낫다.

## 1. 입력

- **CPU:** 10-14 Docker DRAM 재생(264 trace, 명령 13,600개)의 10 ms CPU 수요를 썼다. 11-13 simulator의 cap30 profile과 같다(`cap_sweep.load_profiles`). LLM 대기는 기록된 응답 간격이다.
- **메모리:** 같은 재생의 cgroup `memory_bytes`에서 명령마다 두 값을 뽑았다.
  - 시작 때 메모리(상태): 중앙값 0.02 GiB, p90 0.95 GiB.
  - 명령 중 최고점 − 상태(새 메모리): 무거운 명령의 중앙값 0.17 GiB, p90 1.7 GiB, 최대 18 GiB.
- **예약:** guest 크기다. `sandbox.guest_memory_mib` 규칙(Docker 최고점의 1.5배, 최소 2 GiB, 최대 24 GiB)을 따라 평균 3.6 GiB, 중앙값 2 GiB다.
- **무거운 명령:** CPU 1초 이상이다(1,552개, CPU의 98%). 폭은 CPU 시간 ÷ 단독 길이이고, 시작 때 미리 안다고 가정했다(oracle). 11-13에서 명령 문자열 분류도 CPU 가중 recall 98.5%였다.

## 2. 모델

| 항목 | 설정 |
|---|---|
| cluster | 16노드, 노드당 48/96/192코어, DRAM 1/2/4 GiB/코어. CXL은 없음, 노드마다 X(expander), 16X를 공유(pool). X = 2 또는 8 GiB/코어 |
| sandbox | 고정된 수의 자리. trace 하나를 끝내면 0.5초 뒤 무작위 새 trace가 들어와 자리를 받아야 한다 |
| 자리 받기 | guest 크기를 예약한다. DRAM만: 노드 합 ≤ D. expander: 노드 합 ≤ D + X. pool: 노드는 DRAM을 먼저 쓰고 넘는 부분을 pool에서 받으며, 넘는 부분의 합 ≤ 16X. 메모리가 맞는 노드 중 power-of-2로 CPU 부하가 낮은 곳을 고른다. 맞는 곳이 없으면 기다린다 |
| CPU | 노드마다 CFS처럼 thread별로 고르게 나눈다(water-filling). 수요 d인 명령은 ceil(d)개 thread다 |
| 메모리 위치 | 실행 중 명령의 새 메모리가 DRAM을 먼저 쓰고, 남은 DRAM에 sandbox 상태를 둔다. 나머지는 CXL에 둔다 |
| tax | CXL에 있는 상태 비율 × (무거운 명령 2%, 가벼운 명령 3%) + CXL로 넘친 새 메모리 비율 × (무거운 명령 60%, 가벼운 명령 5%). tax만큼 명령이 같은 폭으로 길어진다(CPU 시간도 늘어난다). 2%는 11-13 bud05 실측(상태만 CXL)이고, 60%는 11-12 DCD 파일럿의 test·build 중앙값이다 |
| 상주 메모리 | `hwm`(기본): guest는 한 번 쓴 메모리를 돌려주지 않는다. 상태 = 지금까지의 최고점. `actual`: free page reporting처럼 상태 = 그 시점 사용량. 결론은 두 모델에서 같았다(`fine-actual.csv`) |
| 이동 | 무거운 명령이 시작할 때 노드에 폭 + 1코어가 남지 않으면, 예약이 맞고 새 메모리를 받을 DRAM이 있는 노드 중 남는 코어가 가장 많은 곳으로 옮긴다. 그 노드가 지금보다 1코어 이상 많을 때만 옮긴다. 명령은 옮기는 동안 멈춘다. hand-off: 10 ms. 복사: 10 ms + (상주 메모리 + 0.1 GiB) ÷ NIC 속도. expander와 DRAM만 구성은 복사만, pool은 hand-off만 쓴다 |
| 시간 | 준비 600초 + 측정 2,400초. density(자리 수/코어) 0.5~1.5를 0.05 간격, seed 3개 |
| SLO 최대점 | seed 평균으로 처음 SLO를 어긴 점과 그 앞 점 사이를 선형 보간했다 |

## 3. 더 볼 것

- **메모리가 막을 때 큰 sandbox가 밀린다.** 예약이 큰 trace(대개 CPU도 큰 Java·Rust)는 빈자리를 늦게 얻는다. 그래서 DRAM만 구성은 같은 sandbox 수에서 CPU를 덜 쓴다. 이 때문에 위 표는 sandbox 수가 아니라 사용률로 비교했다. 동기 RL이라면 이 밀림이 step 시간을 늘릴 수 있는데, 여기서는 재지 않았다.
- **예약 대비 실제 상주가 작다.** 상주 메모리(hwm)는 예약의 약 40%다(코어당 1.3~1.9 GiB). 예약 대신 상주 기준으로 memory overcommit을 하면 DRAM만으로도 더 받을 수 있다. 11-18에 전제를 정했다. overcommit은 이미 하고 있고, 그래도 메모리가 sandbox 수를 막는다. 그래서 이 표의 배율은 상주 기준 자리 받기로 다시 돌려야 한다(RESEARCH 1.1).
- **workload가 하나다.** 다언어 build·test 264 trace만 썼다. Python RL처럼 가벼운 workload는 11-13에서 메모리가 막는 동안 CPU 경합이 없었다. 그 경우 용량만으로 충분하고, 이동은 필요 없다.
- **복사 모델이 낙관적이다.** NIC 경합과 출발 노드 CPU를 넣으면 복사 쪽이 더 나빠진다.
- **CXL 장치 대역폭 한계는 넣지 않았다.** 모든 노드가 pool 장치 하나를 같이 쓰면 대역폭 경합이 생긴다. 여기서는 tax를 고정 비율로만 넣었다.
